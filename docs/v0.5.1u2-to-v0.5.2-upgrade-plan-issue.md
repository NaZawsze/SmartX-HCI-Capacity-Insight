# v0.5.1u2 -> v0.5.2 Upgrade Plan Issue

本文单独记录 `v0.5.1u2 -> runner v0.3.1 -> v0.5.2` 的修复规划。问题现象和现场证据见 `docs/v0.5.1u2-to-v0.5.2-upgrade-issues.md`；本文只写修复方案、实施顺序、包版本策略和验收标准。

## UPG-022 v0.5.1u2 到 v0.5.2 升级控制面切换规划

状态：[重新规划] `v0.5.1u2-fix12-projectfiles` 已确认不可用；manifest 与 project files 已修正，但包内 `v0.5.1u2` web-api 镜像内容实际是 v0.5.2。下一步必须执行 `v0.5.1u2-fix13-imageidentity`，把镜像内部身份和最终包内 image tar 身份作为硬闸门。

目标：

- `v0.5.1u2` 仍作为桥包，不提前迁移平台 project/network/目录。
- runner `v0.3.1` bootstrap 后可以接收旧 web-api 提交的 v0.5.2 任务，同时具备操作 v0.5.2 目标目录的宿主机视角。
- `v0.5.2` 平台切换后，web-api、runner、Prometheus、任务目录和 compose-runtime 全部进入 `/data/smartx-storage-forecast/*` 单根布局。
- `legacy.cleanup` 不再由仍挂载旧目录的 runner 执行；旧环境清理前必须完成 runner handoff。

## 当前已确认问题

### v0.5.1u2-fix11 桥包 manifest 错误

任务：

```text
upgrade-9c6e2392dc12b1ba
```

结果：

```text
status=precheck_failed
message=Runner 缺少升级能力：backup.v1, compose.v1, files.v1, health.v1, image.v1, rollback.v1
```

根因：

- `v0.5.1u2` 是桥包，必须能由源环境 runner v0.3.0 执行。
- `fix11` manifest 错误写入 `minimum_runner_version=v0.3.1`。
- `fix11` manifest 错误使用 v0.3.1 大类能力：`backup.v1/image.v1/files.v1/compose.v1/health.v1/rollback.v1`。
- `source_compatibility.supported_versions=[]`，来源版本兼容列表为空。

修复方向：

- `v0.5.1u2` 不写 `minimum_runner_version`。
- `v0.5.1u2` 使用旧 action 能力：`backup.create/image.load/files.sync/compose.override/compose.apply/health.http/rollback.restore`。
- `source_compatibility.supported_versions` 必须包含 `v0.5.0/v0.5.1/v0.5.1u1/v0.5.1u2`。

### v0.5.1u2-fix12 首次打包 project files 错误

包：

```text
/home/user1/codex-build/packages-v051u2-fix12/01-v0.5.1u2-fix12/smartx-capacity-insight-upgrade-v0.5.1u2.tar.gz
sha256=475beeeb2a25f77fcbd29a23b3449474a742fa0cd437ccda4e3bd1d734ccbfc6
status=DO NOT USE
```

已通过部分：

```text
version=v0.5.1u2
minimum_runner_version=None
required_capabilities=backup.create,image.load,files.sync,compose.override,compose.apply,health.http,rollback.restore
source_compatibility.supported_versions=v0.5.0,v0.5.1,v0.5.1u1,v0.5.1u2
no environment_transitions
no legacy_cleanup
no images/upgrade-runner.tar
no images/prometheus.tar
```

失败证据：

包内 `project/docker-compose.release.yml` 仍是 v0.5.2 目标布局：

```text
name: smartx-hci-capacity-insight
SMARTX_COMPOSE_PROJECT_NAME: smartx-hci-capacity-insight
/data/smartx-storage-forecast/...
name: smartx-hci-capacity-insight-net
subnet: 10.249.251.0/24
```

根因：

- 当前代码目录已经是 v0.5.2 目标布局。
- `scripts/build_upgrade_package.py` 的 `collect_project_files()` / copy 阶段直接把当前 worktree 的 `docker-compose.release.yml`、`docker-compose.offline.yml`、`docker-compose.yml` 打进任意目标版本包。
- 因此 `v0.5.1u2` manifest 虽然已经像桥包，但 project files 仍会把 v0.5.2 的 project/network/目录提前同步到现场。

结论：

- 当前 `v0.5.1u2-fix12` 包不可用。
- 必须修复打包器，让 `v0.5.1u2` 按版本选择 legacy project files。
- 不能通过手工临时改仓库根目录 compose 再改回的方式打包；这会再次制造不可追踪的包差异。

### 第一次 v0.5.2 任务清理失败

任务：

```text
upgrade-7ec51888399c5b74
```

结果：

```text
backup -> load images -> filesystem.prepare -> files.sync
-> task.migrate_runtime_state -> compose.override -> compose.project_migrate
-> compose.apply -> health.http -> task.sync_runtime_state
全部 succeeded

legacy.cleanup failed:
[Errno 16] Device or resource busy: PosixPath('/opt/smartx-storage-forecast')
```

根因：

- 执行 `legacy.cleanup` 的 runner 仍挂载 `/opt/smartx-storage-forecast`。
- 旧 runner 容器 `smartx-storage-forecast-upgrade-runner-1` 仍运行，并占用旧目录。
- 旧 runner 还挂载 `/data/upgrades`、`/data/compose-runtime`、`/prometheus-data` 等待清理路径。

### 第二次同版本 v0.5.2 任务没有被 runner 接手

任务：

```text
upgrade-f247b607ec29f8a4
```

结果：

```text
status=pending
message=升级任务已提交，等待 upgrade-runner 执行
```

根因：

| 组件 | 容器内路径 | 宿主机来源 |
| --- | --- | --- |
| web-api | `/data/upgrades` | `/data/smartx-storage-forecast/upgrades` |
| upgrade-runner | `/data/upgrades` | `/data/upgrades` |

web-api 把任务写到新目录：

```text
/data/smartx-storage-forecast/upgrades/upgrade-f247b607ec29f8a4/task.json
```

runner 仍扫描旧目录：

```text
/data/upgrades
```

所以 runner 看不到任务。

## 设计原则

- 旧 web-api 提交 v0.5.2 任务时，runner 必须仍能读取旧 `/data/upgrades`。
- v0.5.2 cutover 后，新 web-api 必须读取新 `/data/smartx-storage-forecast/upgrades`。
- 任务状态迁移必须在 cutover 前完成，并在 cutover 期间双写。
- 旧环境清理必须在最终健康通过后执行。
- 清理旧目录前，执行 cleanup 的 runner 不能再挂载任何待删除旧目录。
- 禁止用手工清理作为产品修复；手工操作只能用于恢复测试环境。

### corrected v0.5.1u2-fix12

已确认需要。原因是 v0.5.2 平台任务的 `execution_plan` 由当前 `v0.5.1u2` web-api 在点击开始升级时编译；如果桥包仍使用旧 compiler，即使 v0.5.2 包 manifest 声明 `runner.handoff.v1`，任务中也不会出现 `runner.handoff_target_runtime` action。

用途：

- 保持 `v0.5.1u2` 桥包边界不变，不迁移平台 project/network/目录。
- 保持 runner bootstrap 能继续扫描旧 `/data/upgrades`，接收 v0.5.1u2 web-api 提交的 v0.5.2 任务。
- 让 v0.5.1u2 web-api 能编译 v0.5.2 的 `runner.handoff_target_runtime` execution action。
- 让 runner bootstrap/upgrade compose 具备目标 `/data/smartx-storage-forecast/*` 宿主机路径变量，特别是 `SMARTX_HOST_UPGRADES_PATH`。

边界：

- 仍是桥包。
- 仍使用旧 project/network。
- 不加入 `legacy_cleanup`。
- 不加入 `minimum_runner_version`。
- 不加入 `environment_transitions`。
- 不提前迁移平台三件套或 Prometheus。
- 包内 project files 必须是 v0.5.1/v0.5.1u2 legacy 布局，不能使用当前 v0.5.2 目标布局。

### 3. 修复 task runtime state 迁移

修改范围：

- `backend/app/upgrade_runner/actions.py`
- `backend/app/upgrade_runner/engine.py`

行为：

- `task.migrate_runtime_state` 从当前 runner 可见的旧任务目录读取：

```text
context.upgrades_path / context.task_id
```

- 写入目标目录时必须通过 host path 映射：

```text
target_upgrades_path=/data/smartx-storage-forecast/upgrades
```

- 如果当前 action 是 `runner.handoff_target_runtime` 且 runner 被重建，旧进程可能中断。

## UPG-023 v0.5.2 成功后 post-upgrade execution_plan 清理方案

状态：`PLANNED`，作为 cleanupfix3 的替代/收敛方案评估。该方案的核心变化是：`v0.5.2` 平台升级主任务只负责把新平台切换成功、迁移 task 状态并让新控制面可用；旧环境清理不再强行塞进同一个旧 runner 正在执行的主任务尾部，而是在 v0.5.2 成功后，由新 web-api 和新 runner 创建一个独立的 post-upgrade cleanup execution plan。

### 为什么要换思路

cleanupfix2 已证明：

- 主平台切换可以成功，`v0.5.2 + runner v0.3.1` 新环境能健康运行。
- 失败点不是平台不可用，而是旧 runner 仍挂载旧目录，导致 `legacy.cleanup` mount guard 正确拒绝删除 `/opt/smartx-storage-forecast`。
- 同一条任务跨旧 runner、新 runner、旧 `/data/upgrades`、新 `/data/smartx-storage-forecast/upgrades` 四个状态边界，复杂度过高；任何一个状态同步遗漏都会表现为任务 404、history 为空或 cleanup 失败。

因此更稳的切分是：

```text
主升级任务：
v0.5.1u2 + runner v0.3.1
  -> 启动 v0.5.2 新平台
  -> 新 web-api、新 runner、新 Prometheus 健康
  -> 当前 task 状态迁入新 upgrades
  -> 主任务标记 success

后置清理任务：
v0.5.2 新 web-api
  -> 生成 post-upgrade cleanup task
  -> v0.5.2 新 runner 执行
  -> 停止旧 runner/旧 project
  -> 删除旧 network/旧目录/误写残留
  -> 清理任务 success 或 warning
```

### 方案边界

- `v0.5.1u2-fix13-imageidentity` 不再改，除非验证证明它不能编译主升级所需 execution plan。
- `runner v0.3.1-handofffix1` 优先不改，除非新方案仍需要 runner 新原子能力。
- `v0.5.2` 包需要改，因为 post-upgrade cleanup 的调度逻辑、manifest 字段和 v0.5.2 web-api 代码都来自 v0.5.2 包。
- 不放宽 `legacy.cleanup` mount guard。后置清理前仍必须检查旧路径是否被当前有效 runner 挂载。
- 不把旧环境残留当作主升级失败。只要 v0.5.2 新平台健康，主升级成功；旧环境清理失败进入告警/任务中心，允许用户重试。
- 旧 project、旧 network、旧目录的自动删除仍必须做，但它是 v0.5.2 成功后的独立收尾，不再阻断平台版本升级成功。

### manifest 设计

在 v0.5.2 平台包 manifest 中保留 `legacy_cleanup` allowlist，但把执行时机改成 post-upgrade：

```json

  "post_upgrade": {
    "create_cleanup_task": true,
    "cleanup_task_policy": "after_platform_health_success",
    "cleanup_failure_severity": "warning"
  },
  "legacy_cleanup": {
    "legacy_projects": ["smartx-storage-forecast"],
    "legacy_networks": ["smartx-storage-forecast_smartx-net"],
    "legacy_paths": [
      "/opt/smartx-storage-forecast",
      "/data/upgrades",
      "/data/backups",
      "/data/exports",
      "/data/compose-runtime",
      "/data/smartx-capacity-insight-data",
      "/prometheus-data"
    ],
    "target_app_residual_paths": [
      "/data/smartx-storage-forecast/app/upgrades",
      "/data/smartx-storage-forecast/app/backups",
      "/data/smartx-storage-forecast/app/exports",
      "/data/smartx-storage-forecast/app/compose-runtime",

  }

```

要求：

- `legacy_cleanup` 仍只允许出现在 v0.5.2 平台包。
- `v0.5.1u2` 和 runner 组件包不得携带 `legacy_cleanup`。
- post-upgrade task 的 execution plan 由 v0.5.2 web-api 编译，不再由 v0.5.1u2 web-api 编译。
- 后置清理 task 必须记录 `parent_task_id`，方便从主升级任务追溯。

关键点：

  - `version=v0.5.2`
  - `runner_version=v0.3.1`
  - `checks.directories=true`
  - `checks.database=true`
  - `checks.prometheus=true`
- `task.sync_runtime_state` 必须确认当前 task 已写到 `/data/smartx-storage-forecast/upgrades/<task_id>/task.json`。
- `post_upgrade.schedule_cleanup` 由旧 runner 触发一个轻量请求或写一个调度 marker；真正的 cleanup task 由新 web-api 接管创建。

### 后置 cleanup execution_plan

后置 cleanup task 由 v0.5.2 新 web-api 创建，任务类型建议为：

```text

```

```text

```

各步骤要求：

- `post_cleanup.precheck_target_health`
  - 确认当前平台是 `v0.5.2`。
  - 确认当前 runner 是 `v0.3.1`。
  - 确认当前 compose project 是 `smartx-hci-capacity-insight`。
  - 确认当前新数据目录存在并可写。
- `runner.stop_legacy_runtime`
  - 只停止旧 project 下的 `smartx-storage-forecast-upgrade-runner-1`。
  - 禁止停止当前容器 id。
  - 禁止停止 `smartx-hci-capacity-insight-upgrade-runner-1`。
  - 旧 runner 不存在时幂等成功。
- `compose.stop_legacy_project`
  - 只针对 `smartx-storage-forecast` project。
  - 停止并删除旧 `web-api`、`collector-worker`、`frontend`、`prometheus`、`upgrade-runner` 容器。
  - 不执行 `down -v`。
- `network.remove_legacy`
  - 只删除 `smartx-storage-forecast_smartx-net`。
  - 如果仍有非 allowlist 容器连接，跳过并记录 warning。
- `filesystem.cleanup_legacy_paths`
  - 只删除 allowlist 路径。
  - 禁止删除 `/`、`/data`、`/opt`、空路径、包含 `..` 的路径。
  - 禁止删除 `/data/smartx-storage-forecast` 正式目标根目录。

  - 新平台健康仍为 true。
  - 旧 runner 不存在。
  - 旧 network 不存在或已明确 warning。
  - 每个 allowlist 路径记录 `deleted/missing/skipped/failed`。

## UPG-025 v0.5.2 镜像版本控制与 bundle 语义修复计划

背景：

- 当前 v0.5.2 源码 compose 仍允许 `.env` 通过 `SMARTX_IMAGE_TAG` / `SMARTX_RUNNER_IMAGE_TAG` 控制镜像 tag。
- 这对源码构建不同版本有用，但正式升级包中的 compose 如果也保留变量，会让现场 `.env` 残留重新控制启动镜像。
- 现有 `.env` 迁移逻辑会在复制旧 `.env` 时移除镜像 tag key，但目标 `.env` 已存在时直接 `preserved` 返回，仍可能留下旧版本 key。

## UPG-041 升级后自动采集实施计划

根因：v0.5.2 只迁移历史数据并执行健康检查/清理，没有升级后采集动作。历史样本超出当前窗口时概览为 0，旧 `vm_latest.name` 为 VM ID 时也不会自动刷新。

实现：

1. v0.5.1u2 compiler 根据 `post_upgrade.auto_collection=true` 生成 `post_upgrade.schedule_collection`，位置在平台健康和 task sync 后、cleanup/handoff 前。
2. runner v0.3.1 在目标 upgrades 父任务目录写原子 marker，task ID 为 `post-upgrade-collection-<parent_task_id>`。
3. v0.5.2 collector-worker 每 5 秒扫描 marker，父任务成功后只消费一次，并通过现有 CollectionService 更新 SQLite、metric snapshot 和任务中心。
4. 自动采集失败为 warning，主升级和 post-cleanup 保持 success；worker 中断不得重复采集。
5. 重打 UPG-041 三包并仅在 10.20.11.3 从 v0.5.1 正常业务库验证完整链路。

验收：自动采集任务 success；Prometheus 有当前样本；概览容量非 0；CloudTower 返回真实名称时 `vm_latest.name != vm_id`；旧目录/network 清理完成。

## UPG-042 Tower 凭据与 `.env` 成对迁移修复

根因：Tower 名称、地址、用户名和加密后的密码/API Token 保存在 `smartx.db`，解密密钥保存在旧项目 `.env`。当前 `filesystem_prepare()` 先处理 `.env`，且目标 `.env` 已存在时无条件保留；随后再迁移旧 DB。预安装、失败重试或默认目录留下的目标 `.env` 会因此和旧 DB 密文错配。

修复：

1. 先完成业务 DB 选择/迁移，再迁移 `.env`。
2. 迁入 legacy DB 时，legacy `.env` 候选优先于目标 `.env`，但必须通过真实解密校验。
3. runner 使用已经加载的目标 web-api helper 镜像运行 `InventoryService` 解密检查；只返回加密字段数量和兼容结果，不输出密钥、密码或 Token。
4. 目标 DB 存在加密 Tower 凭据时，所有候选 `.env` 均不兼容则主升级失败；不得创建默认密钥，不得进入 compose 切换和旧目录清理。
5. 来源 DB 没有加密 Tower 凭据时，继续支持新/空环境生成默认 `.env`。

验收：从具有配套 `smartx.db + /opt/smartx-storage-forecast/.env` 的 v0.5.1 基线升级；最终 Tower 配置和凭据无需重新填写，升级后自动采集成功。
