## Phase 32 v0.5.1u2-fix9/fix10 Runner Active Version 与组件升级显示修复

状态：已完成

### 背景

- `v0.5.1u2` 是桥包，平台仍运行在旧 project/network：`smartx-storage-forecast` / `smartx-storage-forecast_smartx-net`。
- `v0.5.1u2` 的关键职责是由 web-api 直接执行 runner bootstrap，将 `upgrade-runner` 从 `v0.3.0` 升级到 `v0.3.1`。
- 现场 `10.20.11.12` 已证明 runner bootstrap 实际成功：`/api/system/health.runner_version=v0.3.1`，活动 runner 容器为 `smartx-hci-capacity-insight-upgrade-runner-1:v0.3.1`，DB heartbeat 也是 `v0.3.1`。
- 页面仍可能显示 `v0.3.0` 或执行步骤“未执行”，说明问题不是 runner 未升级，而是 web-api/前端对 active runner version 与组件任务状态的模型不完整。

### 根因决策

- web-api 镜像内置 `/app/RUNNER_VERSION=v0.3.0` 只能表示 `v0.5.1u2` 桥包默认搭配的 runner baseline，不能表示当前活动 runner 版本。
- 当前活动 runner 版本只能来自：
  - 新鲜的 `upgrade_runner_state.runner_version` heartbeat。
  - 正在运行的 runner 容器 Docker image tag。
  - 正在运行的 runner 容器 `/app/RUNNER_VERSION`。
- web-api 不允许用自己的 `/app/RUNNER_VERSION` 自证 runner 当前版本；否则平台容器和 runner 容器分离后失去相互监督意义。
- runner 组件升级任务必须稳定公开为 `kind=component`、`component=upgrade-runner`，即使底层 task.json 只有 `components=["runner"]` 或历史任务缺少 `component` 字段。
- 前端组件页必须绑定真实 task steps，不允许用平台默认步骤渲染 runner 组件任务，否则会出现任务中心成功但页面主体仍显示“未执行”。

### 实施计划

  - heartbeat 超过 30 秒视为过期。
  - heartbeat 过期或缺失时，查询 Docker 中 running 的 `upgrade-runner` 容器。
  - Docker fallback 优先读活动 runner 容器 `/app/RUNNER_VERSION`，再解析 image tag。
  - 完全检测不到 runner 时返回“未检测到 runner”，不能回退成 web-api baseline。

## Phase 34 v0.5.2 Prometheus Compose 重建修复计划

状态：已完成，phase34 包已构建并在 `10.20.11.3` 完整升级链路验证通过

### 背景与目标

- `10.20.11.3` 已按默认目录 `/data/smartx-storage-forecast/project` 从干净链路验证：
  - `v0.5.1 + runner v0.3.0`
  - `v0.5.1 -> v0.5.1u2`
  - `runner v0.3.0 -> v0.3.1`
  - `v0.5.1u2 -> v0.5.2`
- v0.5.2 平台和 runner 升级成功，最终接口为 `version=v0.5.2`、`runner_version=v0.3.1`。
- 剩余问题：最终 `/api/system/health` 返回 `prometheus=false`，因为旧 project 被清理后没有新建 `smartx-hci-capacity-insight-prometheus-1`。
- 用户确认：本轮 v0.5.2 不把 Prometheus 做成单独组件，不额外打包 Prometheus 镜像；Prometheus 应作为 v0.5.2 平台 compose 重建服务之一。

### 根因

- v0.5.2 包内 `project/docker-compose.offline.yml` 已包含 `prometheus` 服务。
- 但升级执行计划根据 manifest `components[].services` 生成 `compose.apply` 的服务列表。
- 当前 v0.5.2 manifest 只声明平台三件套：`web-api`、`collector-worker`、`frontend`。
- 因此 runner 最终只执行三件套 `docker compose up -d`，不会自动启动 compose 文件里未声明的 `prometheus`。
- `compose.project_migrate` 删除旧 `smartx-storage-forecast` project 容器时会删除旧 Prometheus，随后未创建新 Prometheus，导致健康检查失败。

### 设计决策

- 不新增 Prometheus 组件包，不在任务中心引入新的组件概念。
- 不把 `prometheus` 声明成独立 `observability` 组件。
- 将 `prometheus` 加入 v0.5.2 平台组件的 `services` 列表，使同一个平台升级任务执行：
  - `web-api`
  - `collector-worker`
  - `frontend`
  - `prometheus`
- Prometheus 镜像不写入平台包 `images/`，manifest 中不声明 Prometheus image archive。
- v0.5.2 预检查必须检查本地存在 `prom/prometheus:v2.55.1`；缺失时预检查失败并提示先导入镜像。
- Prometheus 数据目录固定保留 `/data/smartx-storage-forecast/prometheus`，升级中不得删除该目录。

## Phase 35 v0.5.2 成功后旧环境残留自动清理计划

状态：已实现并生成 `v0.5.2-cleanupfix1` 包，待 `10.20.11.3` 完整正常升级链路验证

### 背景

- 当前 `v0.5.2-fix2` 已能完成平台、runner、Prometheus 切换，最终健康可达到 `ok=true`、`version=v0.5.2`、`runner_version=v0.3.1`、`checks.prometheus=true`。
- 但升级完成后仍可能留下旧 runner 容器、旧 network、旧目录，以及旧 runner `/data` 绑定误写到新 app 目录下的运行产物。
- v0.5.2 切换后，新 web-api 读取 `/data/smartx-storage-forecast/upgrades`，而正在执行的任务状态可能还停留在旧 `/data/upgrades/<task_id>/task.json`，导致任务中心或状态接口短暂 404。

### 目标

- 在 v0.5.2 升级成功后自动清理旧 project、旧 network 和明确 allowlist 内的旧目录。
- 清理必须发生在最终健康检查之后，不能在平台未健康时删除排障和回滚材料。
- 清理前必须保证当前升级任务最终状态已经写入 `/data/smartx-storage-forecast/upgrades`。
- 清理失败不能把已经健康的 v0.5.2 平台回滚，但必须在任务详情中记录 warning。

## Phase 32 v0.5.1u2-fix9 Runner Active Version 根因发现

- 用户目标是平台容器和 runner 容器相互执行、相互监督：web-api 管理和观测 runner，runner 执行并上报 heartbeat；web-api 不能用自己的构建基线自证 runner 当前版本。
- `10.20.11.12` 真实现场证明 runner bootstrap 已成功：
  - `/api/system/health.runner_version=v0.3.1`
  - 活动 runner 容器是 `smartx-hci-capacity-insight-upgrade-runner-1`
  - 活动 runner image tag 是 `nazawsze/smartx-hci-capacity-insight-upgrade-runner:v0.3.1`
  - 活动 runner 容器内 `/app/RUNNER_VERSION=v0.3.1`
  - `upgrade_runner_state.runner_version=v0.3.1`
- `smartx-storage-forecast-web-api-1` 容器内 `/app/RUNNER_VERSION=v0.3.0`，这是 `v0.5.1u2` 桥包内置 baseline，不是当前活动 runner 版本。
- 页面或接口如果显示 `v0.3.0`，说明它读到了错误来源：
  - web-api 自己的 `/app/RUNNER_VERSION`
  - 已退出的旧 runner 容器 `smartx-storage-forecast-upgrade-runner-1:v0.3.0`
  - 前端初始化缓存 `defaultComponentInfos.version=v0.3.0`
  - 或组件任务未正确关联后没有刷新 active runner state。
- `RUNNER_VERSION` 在 web-api 内应改名或按语义视为 `bundled_runner_baseline_version`；页面上的 runner 当前版本应只使用 `active_runner_version`。
- active runner version 的合理来源优先级：
  1. 新鲜的 `upgrade_runner_state` heartbeat，heartbeat 超过 30 秒视为过期。
  2. running runner 容器的 `/app/RUNNER_VERSION`。
  3. running runner 容器 Docker image tag。
  4. 都没有时显示“未检测到 runner”，不能回退为 web-api baseline。
- 组件升级页面执行步骤“未执行”的直接原因是前端把组件任务和选中组件绑定得过窄，只认 `task.component === selectedComponent.service`；真实或历史 runner bootstrap task 可能只有 `components=["runner"]`，导致任务中心能显示成功但组件页主体不渲染真实 steps。
- 第 8 版 fix 失败的原因是测试夹具假设 `component="upgrade-runner"`，没有使用真实现场 task 形态：`status=success`、`component` 缺失、`components=["runner"]`、6 个 succeeded steps。

## Phase 34 v0.5.2 Prometheus 健康失败根因发现

- `10.20.11.3` 已从默认目录 `/data/smartx-storage-forecast/project` 重新部署并验证完整链路：`v0.5.1 + runner v0.3.0 -> v0.5.1u2 + runner v0.3.0 -> runner v0.3.1 -> v0.5.2`。

  - `smartx-hci-capacity-insight-collector-worker-1`
  - `smartx-hci-capacity-insight-frontend-1`
  - `smartx-hci-capacity-insight-upgrade-runner-1`
- 最终 `/api/system/health` 返回 `version=v0.5.2`、`runner_version=v0.3.1`，但 `checks.prometheus=false`。
- 现场只剩 `smartx-hci-capacity-insight-net`，旧 `smartx-storage-forecast_smartx-net` 已被删除。
- 现场没有 Prometheus 容器：
  - `smartx-storage-forecast-prometheus-1` 不存在。
  - `smartx-hci-capacity-insight-prometheus-1` 不存在。
  - `127.0.0.1:9090/-/healthy` 连接失败。
- 根因不是 Prometheus 数据目录丢失，而是升级执行计划未启动 Prometheus 服务：

## Phase 35 v0.5.2 旧残留自动清理与任务状态迁移发现

- `v0.5.2-fix2` 已能让最终健康达到 `ok=true`、`version=v0.5.2`、`runner_version=v0.3.1`、`checks.prometheus=true`，但升级后仍存在旧环境残留治理问题。
- 已知残留包括旧 project runner 容器、旧 network、旧 `/opt` 或 `/data` 顶层运行目录，以及旧 runner `/data` 绑定误写进 `/data/smartx-storage-forecast/app` 的运行产物目录。
- 旧残留不能在 v0.5.2 健康检查前删除。原因是健康失败时这些目录和容器仍可能是排障、回滚或恢复依据。
- v0.5.2 切换后，新 web-api 读取 `/data/smartx-storage-forecast/upgrades`，但正在执行的任务状态可能仍写在旧 `/data/upgrades/<task_id>/task.json`。如果直接清理 `/data/upgrades`，会造成任务中心丢最终状态。
- 正确模型是先迁移并镜像写入任务状态，再进行健康检查，最后确认新 upgrades 目录中已有最终状态，才允许清理旧 `/data/upgrades`。
- 清理必须由 runner 执行，而不是普通 web-api cleanup service。原因是清理旧 project 容器、network 和宿主机路径需要 Docker socket 与宿主机路径视角，并且必须串在升级 execution plan 的最终健康之后。
- 清理对象必须来自 v0.5.2 manifest 中的固定 allowlist，不能根据环境变量或用户输入拼接。需要显式拒绝 `/`、`/data`、`/opt`、`/data/smartx-storage-forecast` 以及目标正式子目录。
- 清理失败应作为升级任务 warning 记录，不应把已健康运行的 v0.5.2 平台回滚；但健康检查失败时必须跳过清理。

## Phase 36 v0.5.1u2-fix12 project files 根因发现

- `v0.5.1u2-fix12-first` 的 manifest 已修正为桥包语义，但包仍不可用。
- 静态闸门失败点在 project files：包内 `project/docker-compose.release.yml` 使用当前 v0.5.2 worktree 的新布局。
- 具体错误值包括 `name: smartx-hci-capacity-insight`、`SMARTX_COMPOSE_PROJECT_NAME: smartx-hci-capacity-insight`、`smartx-hci-capacity-insight-net`、`/data/smartx-storage-forecast/*` 和 `10.249.251.0/24`。
- 根因是 `scripts/build_upgrade_package.py` 对任意目标版本都直接复制当前 worktree 的 compose 文件；当前 worktree 已经是 v0.5.2 目标布局，所以打 `v0.5.1u2` 包会把新布局提前带进去。
- 正确模型是 project files 也必须版本化：`v0.5.1u2` 使用 legacy project/network/目录，`v0.5.2` 使用 target project/network/目录。
- 不能通过手工临时改 compose 文件来打包，因为这种包无法复现，也容易再次污染 v0.5.2 源文件。

## Phase 37 v0.5.1u2-fix12 镜像污染根因发现

- `v0.5.1u2-fix12-projectfiles` 已通过 manifest 和 project files 静态闸门，但完整链路第一步仍失败。
- 失败现象具有迷惑性：升级任务为 `succeeded`，容器镜像 tag 显示为 `v0.5.1u2`，但 `/api/system/health` 返回 `version=v0.5.2`。
- 容器内直接证据证明 tag 内容被污染：
  - `/app/VERSION=v0.5.2`
  - `/app/RUNNER_VERSION=v0.3.1`
  - `app/core/config.py` 与 `app/v2/config.py` 中默认版本也为 `v0.5.2` / `v0.3.1`
- 因此 `nazawsze/smartx-hci-capacity-insight-web-api:v0.5.1u2` 这个 tag 在构建宿主机上并不可信；它实际指向了 v0.5.2 内容。
- 之前的打包流程错误点是：可以在 `build_images=False` 或 `check_version_metadata=False` 情况下保存已有 tag 到升级包，导致污染镜像绕过了打包阶段。
- 后续不能再只相信：
  - Docker tag。
  - manifest version。
  - compose image 字段。
  - 本地源码中的版本常量。
- 正确验证对象必须是“最终升级包内 image tar 的镜像内部身份”。
- `v0.5.1u2` 桥包的正确身份应为：
  - 平台版本：`v0.5.1u2`
  - web-api 内置 runner baseline：`v0.3.0`
  - manifest 不要求 `minimum_runner_version`
  - manifest 不携带 v0.3.1 才有的新能力要求
- `v0.5.2` 平台包的正确身份应为：
  - 平台版本：`v0.5.2`
  - web-api 内置 runner baseline：`v0.3.1`
  - manifest 可要求 runner v0.3.1 提供的新能力
- fix13 的核心不是“再打一遍包”，而是让污染 tag 复用不可能静默进入包：本地镜像身份、最终 tar 内镜像身份、完整链路节点验收三层都必须检查同一件事。

## Phase 45 v0.5.2 镜像版本控制与 bundle 语义发现

- `.env` 应视为现场运行配置，不应再作为发布版本控制器。
- 正式升级包内 project compose 不能保留 `SMARTX_IMAGE_TAG` / `SMARTX_RUNNER_IMAGE_TAG` 这类版本变量，否则现场残留 `.env` 可能把升级后的容器重新拉回旧 tag。
- 源码根目录 compose 可以继续保留变量，作为打 `v0.5.1u2`、`v0.5.2` 等不同目标版本的模板；但进入升级包的 compose 必须在打包阶段渲染成固定 tag。
- `.env` 中以下 key 必须从正式运行配置中移除：
  - `SMARTX_IMAGE_TAG`
  - `SMARTX_RUNNER_IMAGE_TAG`
  - `SMARTX_APP_VERSION`
  - `SMARTX_RUNNER_VERSION`
- 当前 `_migrate_env_file()` 在目标 `.env` 已存在时直接 preserve，这会绕过 sanitize；应改为“目标存在也 sanitize 后重写”，只保留密钥、账号、DB、Prometheus URL、采集时间、CORS 等运行配置。
- `scripts/build_bundle_upgrade_package.py` 当前组合包 manifest 未透传 platform manifest 的 v0.5.2 迁移语义，至少包括：
  - `minimum_runner_version`
  - `source_compatibility`
  - `environment_transitions`
  - `directory_transition`
  - `legacy_cleanup`
  - `post_upgrade`
- 如果 bundle 包缺这些字段，从旧版本升 v0.5.2 时可能不会执行单根目录迁移、任务状态迁移、runner target runtime handoff 和 post-cleanup。
- Prometheus chown helper 失败应在 `filesystem.prepare` 阶段明确失败；不能只靠后续 Prometheus 健康检查间接暴露。
- 本轮计划已写入：
  - `docs/v0.5.1u2-to-v0.5.2-upgrade-plan-issue.md` 的 `UPG-025`
  - `docs/v0.5.1u2-to-v0.5.2-upgrade-issues.md` 的 `UPG-025`
  - `task_plan.md` 的 `Phase 45`

## Phase 49 UPG-038 v0.5.2 业务数据迁移门禁发现

- `10.20.11.3` 最新完整链路中，`v0.5.1u2`、`runner v0.3.1`、`v0.5.2` 和 post-cleanup 任务均显示成功，但业务数据没有迁移成功。
- 升级前业务库基线包含 `towers=1`、`clusters=1`、`vm_latest=522`、`vm_volumes=89529`、`collection_runs=25`。
- 升级后目标库 `/data/smartx-storage-forecast/app/smartx.db` 只有 96K，`towers=0`、`clusters=0`、`vm_latest=0`、`vm_volumes=0`、`collection_runs=1`。
- v0.5.2 task 的 `filesystem.prepare` 和 `compose.project_migrate` checkpoint 均记录 `copied_app_sources=[]`，说明旧业务库没有复制到目标目录。
- post-cleanup 随后删除 `/data/smartx-capacity-insight-data`，导致旧业务源被清理；这是 cleanup 门禁错误，不应只依赖 `health.database=true`。
- 根因是 `filesystem.prepare` 当前以“目标 `smartx.db` 是否存在”作为跳过迁移条件；目标库存在只能说明有 SQLite 文件，不能说明业务数据有效。
- `health.database=true` 当前只执行 `SELECT 1`，因此只能证明 SQLite 可打开，不能证明 `towers/clusters/vm_latest/vm_volumes` 已迁移。
- 正确策略应是“比较后决策”：旧库有业务数据且目标为空/初始化库时自动替换目标库；旧库和目标库都有不同业务数据时硬失败；旧库无业务数据时允许空环境升级。
- 修复必须进入 runner v0.3.1 包，因为实际执行 `filesystem.prepare` 的是 runner；同时 v0.5.2 包需要重打以携带新的 cleanup/verification 门禁。
