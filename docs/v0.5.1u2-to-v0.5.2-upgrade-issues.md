# v0.5.1u2 -> v0.5.2 Upgrade Issues

本文单独记录 `v0.5.1u2 -> runner v0.3.1 -> v0.5.2` 链路中的目录、Compose project/network、历史问题和当前现场问题。主升级链路仍以 `docs/v0.5.0-to-v0.5.2-upgrade-plan.md` 为准；本文用于集中排查问题，避免问题散落在 `docs/upgrade-issues.md`、`task_plan.md` 和包台账中。对应修复规划见 `docs/v0.5.1u2-to-v0.5.2-upgrade-plan-issue.md`。

## 升级链路边界

正确链路：

```text
v0.5.1 + runner v0.3.0
  -> v0.5.1u2 + runner v0.3.0
  -> v0.5.1u2 + runner v0.3.1 bootstrap
  -> v0.5.2 + runner v0.3.1
```

核心边界：

- `v0.5.1u2` 只是桥包，不能迁移平台 project、network 或目录。
- runner `v0.3.1` bootstrap 只负责把 runner 切到新 project/network，不迁移平台三件套和 Prometheus。
- `v0.5.2` 才负责平台 project/network 迁移、单根目录迁移、Prometheus 重建和旧环境清理。

既有修复设计：

## 历史失败模式

### v0.5.1u2 过早引入新 project/network

错误表现：

```text
failed to create network smartx-hci-capacity-insight-net:
invalid pool request: Pool overlaps with other one on this address space
```

根因：

- `v0.5.1u2` 是桥包，但包内 compose 提前使用了 `smartx-hci-capacity-insight` / `smartx-hci-capacity-insight-net`。
- 旧网络 `smartx-storage-forecast_smartx-net` 仍占用 `10.249.249.0/24`，新网络创建或迁移时冲突。

结论：

- v0.5.1u2 必须保留旧 project/network。
- project/network 迁移只能发生在 runner v0.3.1 具备能力后，由 v0.5.2 平台升级执行。

### runner 版本显示长期停留 v0.3.0

根因：

- v0.5.1u2 web-api 曾使用自身镜像内 `/app/RUNNER_VERSION` 作为当前 runner 版本 fallback。
- v0.5.1u2 桥包内置 baseline 是 `v0.3.0`，所以即使活动 runner 已经是 `v0.3.1`，页面仍可能显示 `v0.3.0`。

修复边界：

- 当前 runner 版本必须来自活动 runner heartbeat、运行中 runner 容器内版本文件，或运行中 runner 镜像 tag。
- 不能用 web-api 镜像内 baseline 代表 runner 当前版本。

### runner bootstrap 数据目录挂载错误

历史错误：

- runner bootstrap 使用过 `/data:/data`，导致 runner 写 heartbeat 到宿主机 `/data/smartx.db`，而不是实际业务库。
- 也可能把 `upgrades/backups/exports/compose-runtime` 写入 `/data/smartx-storage-forecast/app`，形成 target app residual。

结论：

- runner bootstrap 必须根据当前 web-api 的 `/data` mount source 推导宿主机 app data path。
- v0.5.2 cleanup 必须允许清理已知 target app residual，但只能在最终健康通过后执行。

### v0.5.2 切换后当前任务状态丢失

历史问题：

- v0.5.2 切换后，新 web-api 读取 `/data/smartx-storage-forecast/upgrades`。
- 正在执行的 v0.5.2 任务状态可能仍在旧 `/data/upgrades/<task_id>/task.json`。
- 前端或任务中心可能对当前任务返回 404 或看不到最终状态。

既有设计：

- `task.migrate_runtime_state` 在 cutover 前把当前任务复制到新 upgrades 目录。
- runner 在 cutover 期间双写 task 状态。
- `task.sync_runtime_state` 确认最终状态已写入新目录后，才允许 `legacy.cleanup` 删除旧 `/data/upgrades`。

发生时间：2026-07-03

根因：

- `runner.handoff_target_runtime` 只启动了新 runner，没有停止旧 project 的 runner。

- `v0.5.1u2-fix13-imageidentity` 已通过正常链路第一跳。
- `runner v0.3.1-handofffix1` 已通过正常链路第二跳。
- `v0.5.2-cleanupfix2` 标记为 `DO NOT USE FOR FINAL CHAIN`，需要 `v0.5.2-cleanupfix3`。
- 修复必须新增旧 runner 下线动作，并修正 task 迁移目标路径；不能通过放宽 `legacy.cleanup` 保护来绕过。

### UPG-025 v0.5.2 镜像版本控制和 bundle 迁移语义风险

状态：LOCAL IMPLEMENTED / WAITING FOR 10.20.11.3 PACKAGE AND CHAIN VALIDATION

专项修复计划：`docs/v0.5.1u2-to-v0.5.2-upgrade-plan-issue.md#upg-025-v052-镜像版本控制与-bundle-语义修复计划`

发现时间：2026-07-07

问题摘要：

- v0.5.2 compose 当前仍允许 `.env` 使用 `SMARTX_IMAGE_TAG` / `SMARTX_RUNNER_IMAGE_TAG` 覆盖镜像 tag。
- `.env` 迁移逻辑在复制旧 `.env` 时会清理镜像 tag key，但目标 `.env` 已存在时直接保留，仍可能留下版本 key。
- `scripts/build_bundle_upgrade_package.py` 合并 platform/prometheus manifest 时，只保留部分平台字段，未透传 v0.5.2 目录迁移和旧环境清理语义。
- Prometheus 目录 chown helper 失败时错误可能延后到健康检查才暴露，排查不直接。

为什么这是问题：

- `.env` 是现场运行配置，不应该作为发布版本控制器。
- 如果 `.env` 残留旧 `SMARTX_IMAGE_TAG`，可能出现“升级成功但 compose 又启动旧 tag”的问题。
- 如果 bundle 包丢失 `directory_transition` / `legacy_cleanup` / `post_upgrade`，从旧版本用 bundle 升 v0.5.2 时可能不会迁移到 `/data/smartx-storage-forecast` 单根目录，也不会创建 post-cleanup。
- v0.5.2 最终版本应该由升级包 manifest、包内固定 compose tag、容器内 `VERSION` / `RUNNER_VERSION` 共同约束，而不是由 `.env` 决定。

### UPG-037 升级重启窗口误报 Internal Server Error 与 verification runner 短窗口

- v0.5.2 主任务成功后，runner handoff 与新 runner heartbeat 之间存在短窗口。

- 不能把 manifest 改成容器内部路径；manifest 表达 host 最终目录，runner 负责运行时路径解释。

- `history()` 改为纯读，只使用内存 completed-runner view，不再持久化历史任务、不投影任务中心、不补调度 cleanup。
- `status()` 保留当前任务完成持久化、任务中心投影和 post-cleanup 调度职责。
- history 按 `created_at -> uploaded_at -> started_at -> finished_at -> updated_at -> task_id` 的首个有效业务时间倒序。
