# 测试架构设计（所有版本通用）

> 定位：**跨版本长期有效的测试架构**——定义分层、测试套餐（Profile）、触发规则、候选轮次演进、
> 标准数据集与工具链。回答三个问题：
> ① 一个改动**必须跑什么**（不可裁剪核心）；
> ② 一个改动**按套餐跑什么**（P0–P4，不是每次都全跑）；
> ③ 一轮候选（rNN）从探索到定稿**每轮跑什么**（不重复烧全量）。
>
> 执行细节（每层的命令、判定标准、证据格式）在 [test-process-and-scope.md](test-process-and-scope.md)；
> 本文只定**结构**，两文冲突时**以本文为准**（架构）。

## 1. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  套餐层：一个改动该跑多少（P0–P4）                            │
│    由「变更类型 → 套餐」自动判定；裁剪必须留痕                 │
├─────────────────────────────────────────────────────────────┤
│  执行层：L0–L6 七层（在哪跑、判定、证据）                      │
│    L0 单元 │ L1 构建门禁 │ L2 安装健康 │ L3 升级链路          │
│    L4 反向缺陷 │ L4.5 并发干扰 │ L5 回滚 │ L6 发布验收        │
├─────────────────────────────────────────────────────────────┤
│  基础设施层：可复用资产（与具体版本无关）                      │
│    · 标准测试数据集（§6）    · verify_data_integrity.py       │
│    · 链路 harness          · 冒烟/自检脚本                    │
│    · 机器基线与重置口径（.3 构建 / .14 验证 / .12 生产等价）   │
└─────────────────────────────────────────────────────────────┘
```

三条主轴：**套餐**（跑多少）× **分层**（怎么跑）× **资产**（用什么跑）。
版本（v0.5.4、v0.5.5、……）只是这套架构的一次实例化。

## 2. 测试套餐（Profile）——"部分测试不需要走全部流程"的正解

### 2.1 套餐定义

| 套餐 | 何时用 | 包含 | 典型耗时 | 放行人 |
| --- | --- | --- | --- | --- |
| **P0 提交冒烟** | 每次代码提交/每次小修 | L0（相关单测 + 全量基线对比） | 3–5 min | 自动（退出码） |
| **P1 功能验证** | 功能改动合入后；每日例行 | L0 全量 + 前端门禁 + **L2**（8 项） | 10–15 min | 执行者 |
| **P2 链路验证** | 改动触及**升级体系**（runner / compose / 安装升级脚本 / 迁移） | P1 + **L3 主路径一条**（CLI） + **L4 相关反向用例** + L4.5 单飞守卫 | 40–60 min | 执行者 + 记录 |
| **P3 候选定稿** | 宣布某 rNN 为发布候选**之前**（每版本一次） | **全部层**：L0–L6；L3 含 Web+CLI 双路径 + 老布局链；矩阵格全回填 | 2–4 h | 用户 |
| **P4 现场热修** | 生产紧急补丁，时间盒受限 | L0 相关 + L1 + L2 + 受影响的**单条** L3 链 + 数据不变性 compare + （触及升级路径则）L5 单场景 | 30–60 min | 用户明示 |

### 2.2 不可裁剪核心（Invariant Core，任何套餐都不得省）

不管跑哪个套餐，以下**永远包含**；裁掉任何一条 = 该轮结论无效：

1. **L0 不新增失败**（与最近全量基线对比，存量失败清单逐个可指认）；
2. **数据完整性 compare**：触及数据/迁移/升级路径时，T0 vs 终态必须全 PASS
   （`verify_data_integrity.py`，含业务表零变化 + `.env` 密钥 + 引用完整性）；
3. **L2 健康 8 项**（只要涉及部署产物）；
4. **升级失败自动回滚生效**（只要本批改动出现在升级计划里）；
5. **证据归档**（跑过就必须留证，哪怕裁剪了其他项）。

### 2.3 变更类型 → 套餐映射（自动判定表）

| 变更类型 | 套餐 | 备注 |
| --- | --- | --- |
| 纯文档 | 不跑 | 但**本文档类**改动需自审一致性 |
| 后端业务逻辑（非升级） | **P1** | + 相关 L0 子集 |
| 前端 | **P1** | 含前端门禁；UI 目视按 §8 表处理 |
| 升级体系（runner/compose/install/upgrade/migrations） | **P2** | 探索轮跑 P2；定稿轮升 P3 |
| 依赖/镜像基础层（requirements、Dockerfile） | **P2** | 必含 L4.5（依赖集差异就是 r38 worker 崩溃的根因） |
| 数据库 schema/迁移 | **P2** | 必含数据完整性 + expand-only 门禁 |
| 安全相关（鉴权/凭据/密钥） | **P2** | 必含 L4 加密可用性 |
| 发布候选定稿 | **P3** | 用户说"发布"前必须已完成 |
| 现场热修 | **P4** | 裁剪清单必须逐项记录在轮次日志 |

**升降级规则**：拿不准时**就高不就低**；执行者可临时升档，**降档必须用户批准**并在文档留痕。

### 2.4 裁剪留痕（防止"悄悄少测"）

每轮执行的记录必须写：

```
本轮套餐：P2
裁剪：L3-b（Web 路径）——理由：本轮未触及 web-api 侧升级入口，仅 runner 改动
不可裁剪核心：已全部执行（列出）
```

**P3 禁止任何裁剪**；P4 允许裁剪但必须给出"接受该风险的依据"。

## 3. 候选轮次演进（rNN 生命周期）——"不每轮烧全量"

一个版本会产生多轮候选（r36→r37→r38→r39→r40 就是实例）。架构规定：

| 轮次性质 | 跑什么 | 依据 |
| --- | --- | --- |
| **探索轮**（每轮修复后重建 rN） | **P2** + 本轮改动直接触及的反向用例（L4 子集） | 重建即作废旧结论；但**不需要**重跑未受影响的层 |
| **回归轮**（某层失败后修复） | 失败层 + 它的下游层（L3 失败 → 重跑 L3+L4）+ 不可裁剪核心 | 不得只补跑失败点（AGENTS：不能只在失败现场补跑） |
| **定稿轮**（宣布候选 ready） | **P3** 全量，矩阵格全回填 | 唯一允许作为"发布验收证据"的轮次 |
| **发布后**（下一版开始） | 定稿轮的候选作为下一版的 **known-good 基线** | 见 §7 基线管理 |

关键口径：**探索轮的结论 = "该轮改动没引入新问题"，不是"候选可发布"**。
只有定稿轮（P3）的结论才能支撑发布——这样既不每轮烧 4 小时，又不让"攒了五轮没全测"溜进发布。

## 5. 环境与机器（长期固定）

沿用既有分工（AGENTS §5）：**`.3` 只构建（L0/L1）**；**`.14` 干净验证（L2/L3/L4）**；
**`.12` 生产等价（L3/L5/L6）**。新增两条架构级约束：

1. **机器角色不得漂移**：临时把 `.12` 当开发机的做法一律禁止（它同时是升级演练机）；
2. **验证机可重置**：`.14` 随时可以全清重装，**不得**在上面存唯一证据副本（证据归档见执行规范 §6）。

## 6. 标准测试数据集（项目资产，与版本解耦）

每次链路测试**不再随手 seed**，统一使用标准数据集（生成脚本进 `scripts/`，画像如下）：

| 维度 | 要求 |
| --- | --- |
| 规模 | ≥ 2 塔、≥ 3 集群、≥ 120 VM、≥ 240 卷（小库跑不出大库问题，规模可参数化） |
| 字符集 | VM/卷名必须含**中文、空格、连字符、emoji**（编码损坏只能靠它暴露） |
| 回收站 | ≥ 3 台 `in_recycle_bin=true` 的 VM（②③ 过滤口径） |
| 创建时间 | 覆盖"本日/本月/历史"三段 + **缺失 `local_created_at` 的回落样本** |
| 边界值 | `used_bytes=0`、超大值（接近 2^53）、空名/长名 |
| 引用 | **不造孤儿行**（引用完整性检查要求 0 孤儿，除非用例本身是造孤儿） |

数据集的**生成结果**不进 Git（属运行时数据），**生成脚本与画像**进 Git。

## 7. 基线管理

1. **known-good 基线**：上一个 P3 定稿轮的平台+runner 包（SHA 记录在台账）。探索轮的"全新安装"
   用它做源端或对照组——新候选的问题要么是新改动引入，要么是基线就有（后者单独立项）；
2. **单测基线**：最近一次全量跑的失败清单（`progress.md`），L0 的判定依据；基线漂移（失败数变化）
   必须逐个定性，不允许"反正以前也挂"；
3. **机器基线**：`.14` 的重置口径 = 全清 + 从候选交付目录全新安装（脚本已固定），
   不维护自定义快照（快照会随版本漂移且不可审计）。

## 8. 与"已知未覆盖项"的关系

[test-process-and-scope.md](test-process-and-scope.md) §8 的未覆盖表按版本滚动维护；
架构层面的长期承诺只有两条：

- **不覆盖 ≠ 不记录**：任何一次验证若因缺塔/缺环境而 WARN，必须留在报告里，不允许静默略过；
- **触发即升级**：未覆盖项被真实场景触发时，自动升为 P3 里的强制项，并回填 §8 的"何时必须补"。
