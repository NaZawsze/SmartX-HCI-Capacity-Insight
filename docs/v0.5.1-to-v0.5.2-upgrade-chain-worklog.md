## Findings Extract

### Phase 45 - Image Tag and `.env` Semantics

Findings:

- `.env` is runtime configuration and must not control release versions.
- Formal upgrade package compose files must not contain:
  - `SMARTX_IMAGE_TAG`
  - `SMARTX_RUNNER_IMAGE_TAG`
  - `SMARTX_APP_VERSION`
  - `SMARTX_RUNNER_VERSION`
- Source compose files may remain templated, but package compose files must be rendered with fixed image tags.
- Target `.env` must be sanitized even when it already exists.
- Bundle package manifests must preserve platform migration semantics:
  - `minimum_runner_version`
  - `source_compatibility`
  - `environment_transitions`
  - `directory_transition`
  - `legacy_cleanup`
  - `post_upgrade`
- Prometheus image is not bundled for v0.5.2, but compose must still start Prometheus using the host-local image.

Impact:

- Prevents old `.env` values from pulling the upgraded platform back to old tags.
- Keeps v0.5.1u2 as a bridge package, not an accidental v0.5.2 migration package.

### Phase 47 / UPG-032 - Old Upgrade History Migration

Problem:

```text
v0.5.2 chain succeeded, but /api/admin/component-upgrade/history became empty.
```

Root cause:

- `task.migrate_runtime_state` only migrated the current v0.5.2 platform task.
- Existing old `/data/upgrades/*/task.json` tasks were not copied to `/data/smartx-storage-forecast/upgrades`.
- Post-cleanup then removed `/data/upgrades`, deleting old runner component task history.

Fix:

- Runner action `task_migrate_runtime_state` now scans the source upgrades root for existing task directories.
- It copies every valid `*/task.json` task directory into the target upgrades root.
- Non-task directories are skipped.

### Phase 48 / UPG-033 - Health Runner Fallback

Problem:

```text
v0.5.2 main task succeeded.
running runner container existed.
first two /api/system/health samples returned runner_version="未检测到 runner".
third sample returned runner_version="v0.3.1".
```

Root cause:

- `UpgradeService.component_version()` already supports runner fallback:
  1. fresh heartbeat
  2. running runner container `/app/RUNNER_VERSION`
  3. running runner image tag
- `/api/system/health` only read heartbeat.
- During runner handoff, the container can be running before it writes a fresh heartbeat.

Fix:

- `backend/app/v2/system/health.py` now falls back to a running `upgrade-runner` container when heartbeat is missing or stale.
- It reads `/app/RUNNER_VERSION` first, then parses the running image tag.
- It still must not fall back to the web-api baseline `RUNNER_VERSION`.
