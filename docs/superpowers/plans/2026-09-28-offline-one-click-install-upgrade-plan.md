# 计划：离线交付一键安装 + 一键升级（49-56）

状态：计划（2026-09-28）。设计见 `docs/superpowers/specs/2026-09-28-offline-one-click-install-upgrade-design.md`；立项见 `task_plan.md` 第 56 项。**待用户批准后实施。**

## 0. 交付物目标形态

```text
smartx-capacity-insight-v0.5.3-offline/
├── README.md                    # 中文使用说明
├── install/                     # 首次部署（运行物料：镜像）
│   ├── install.sh
│   ├── images/*.tar + SHA256SUMS
│   └── project/ + .env.template
└── upgrade/                     # 离线升级（版本单元：包）
    ├── upgrade.sh
    └── packages/*.tar.gz + SHA256SUMS
```

固定口径：管理员 `admin` / `password`；升级走 API；安装落**已发布 runner 基线 v0.3.1**。

## 1. 实施步骤（每步独立提交，可单独回滚）

### 步骤 1 · 交付目录制作工具 `scripts/build_offline_delivery.py`
**为什么先做**：交付目录必须**可复现、可审计**，不能靠手工拼装。

| 输入 | 来源 |
| --- | --- |
| 平台镜像（web-api / collector-worker / frontend） | 从**平台升级包**内的 `images/*.tar` 提取（包是已门禁的产物，天然可审计） |
| prometheus 镜像 | `docker save prom/prometheus:v2.55.1` |
| runner 镜像 | 从 **runner 组件包**内 `images/upgrade-runner.tar` 提取；或 `docker save` |
| `project/` 部署文件 | 仓库（compose 须渲染为 **v0.3.1** 基线） |
| `.env.template` | 仓库 `.env.example`（密钥位留占位符，由安装脚本替换） |
| 升级包 | `.3` 构建产物 + `.sha256` |

**产出**：`--output-dir` 指定的完整交付目录，每个目录一份 `SHA256SUMS`，并**自动跑敏感文件扫描**（复用 `verify_release_docs_safe.py` 的敏感名规则），有敏感件即失败退出。

**验收**：连续两次构建产出结构一致；`SHA256SUMS` 全部 `OK`；敏感扫描 0 命中。

### 步骤 2 · `install/install.sh`
按设计 §4 的 10 步实现。**要点**：
- 前置检查失败要**说清缺什么**（docker / 磁盘 / 端口）
- 幂等：已安装则退出，**不覆盖 `.env`**
- 密钥用 `openssl rand -hex 32`（无 openssl 时用 `/dev/urandom` 兜底）生成，**不打印明文到日志**
- 健康检查轮询带超时，超时打印容器状态 + 最近日志 + 补救命令
- 复用 `pre_install.sh` 的目录/权限逻辑（不重复发明）

**验收**：设计 §7 场景 1/2/3 通过。

### 步骤 3 · `upgrade/upgrade.sh`
按设计 §5 的 9 步实现。**要点**：
- **只调 API**，脚本内不得出现 `docker load` / `compose up` / `rm`
- 预检查逐项打印，任一 false 即停
- 400（单飞守卫）要翻译成人话提示
- 失败按状态给指引（可重试 / 逃生门 / 查日志）
- 轮询终态判定与 `chain_step2.sh` 对齐

**验收**：设计 §7 场景 4/5/6 通过。

### 步骤 4 · `README.md` 中文使用说明
覆盖：交付物说明 / 前置条件 / 目录结构 / 首次安装 / 离线升级 / **8 项自检** / 常见失败与处理 / 卸载（警告数据不可恢复）/ 安全建议（首次登录改口令）。

**要求**：说明里每条命令都要在实测中跑过（设计 §7 场景 7）。

### 步骤 5 · 静态检查 + `.3` 演练
- `shellcheck`（若可用）+ `bash -n` 语法检查
- `.3` 上做一次"类交付目录"的安装/升级演练（不破坏 `.3` 现有实例，用独立目录与 project 名）
- 敏感文件扫描、文档脱敏扫描

### 步骤 6 · **干净 VM 实测**（不可省）
在一台**无历史数据的干净 VM**（全新安装形态）上：
1. `install.sh` 全新安装 → 8 项自检全过
2. **断网**（或屏蔽 DockerHub）→ `upgrade.sh` 离线升级 → 8 项验收全过

**这一步是本需求的交付场景本身**，只在有历史的机器上验不算数。

## 2. 执行顺序与关卡

```
步骤1 制作工具 ──► 步骤2 install.sh ──► 步骤3 upgrade.sh ──► 步骤4 README
                                                    │
                                    步骤5 静态+.3演练 ──► 步骤6 干净VM实测
```

- 每步单独提交，`git diff --check` 通过；
- 步骤 6 不通过 → 不算完成，不写"已交付"；
- 任何一步发现要改平台代码 → 停下评估（超出本项范围）。

## 3. 不做（边界）

- 不做人工回滚（US-29 已决定），沿用失败自动回滚
- 不做安装期 Tower 连通性验证
- 不做多机/集群
- 不做无人值守自动升级（保留人工确认）
- 不改平台业务代码（脚本只调 API）

## 4. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 干净 VM 与客户现场差异（SELinux、防火墙、时间不同步） | 前置检查显式检测并给出处理建议；说明书列出常见环境问题 |
| 交付目录被手工改动 | `SHA256SUMS` 每次运行前校验；README 说明不要改 |
| 升级中断电/断网 | 走逃生门 + 再跑一次升级（US-27 正在加强收尾能力）；说明书写明 |
| 脚本在客户机上是 root 运行 | 脚本只操作自己的交付目录与平台标准路径，不清理宿主其它内容 |
