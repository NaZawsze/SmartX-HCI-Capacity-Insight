## 0b. US-29 放弃人工回滚（2026-09-28 用户决定）

**决定**：下线人工回滚入口，**保留失败自动回滚**。

| # | 位置 | 改法 |
| --- | --- | --- |
| 1 | 前端升级中心 | 隐藏「回滚」按钮/入口（`recovery` 区的 rollback 项一并隐藏） |
| 2 | `api/admin/upgrade.py` | `/rollback/{tid}` 与 `/recovery/{tid}/rollback` **保留路由**（避免老客户端 404），响应加 `deprecated: true`；前端不再暴露 |
| 3 | `service/execution.py::rollback` | 保留实现不动，仅标记废弃（`rollback_deprecated` 任务属性或日志） |
| 4 | 失败自动回滚（`execution.py:345-370`） | **不动**——它是唯一安全网 |
| 5 | 文档 | `docs/releases/CHANGELOG.md` 已知问题、`docs/deployment.md` §10、`docs/upgrade-chain.md` §4 补「不支持人工回滚；失败自动回滚保留；失败后靠逃生门 + 重跑升级收尾」 |
| 6 | 审计矩阵 | US-17 标记 **N/A**（不做人工回滚 → 无需验证） |

**直接后果**：失败后唯一出路 = 逃生门（US-25）→ 标记失败 → **再跑一次成功升级由 post-cleanup 收尾**。因此 **US-27 提为关键路径**。

**验收**：前端无回滚入口；`rollback.restore` 自动路径在 `.12` 失败注入中仍生效（单独验一次，见 roadmap §6 第 2 项）。

## 1. US-26 现场 runner 够用时平台升级仍重建 runner（本批唯一有硬时限）

**设计已出**：`docs/superpowers/specs/2026-09-28-us26-runner-declaration-not-instruction-design.md`（平台包对 runner 只有「声明」没有「指令」；`manifest deploy:false` + compiler 区分 + 动作层 `preserve_current` 兜底 + 组件侧回写 compose；不推翻 49-3 字面量门禁）。

**目标**：现场 runner 版本 ≥ 包 `minimum_runner_version` 时，平台升级**不改动 runner**；低于时预检查本来就该拒绝（现有行为）。

**改点**

| # | 位置 | 改法 |
| --- | --- | --- |
| 1 | `compiler.py:229` | **按设计文档改为：只取 `deploy != False` 的条目 → runner 部署镜像为空 → handoff 动作不重建 runner**（结构上保证平台包无法指挥 runner 版本） |
| 2 | `backend/app/upgrade_runner/actions.py` `compose_override` / `compose_apply` | 目标 tag 与当前运行 tag 相同 → 不带 `--force-recreate`；现场版本更高 → 保留现场版本（与 1 呼应，动作层兜底） |
| 3 | 组件升级侧（`execution.py` 执行链） | 组件升级成功后**回写** `project/docker-compose.yml` 与 `compose-runtime/docker-compose.runner-upgrade.yml` 的 runner tag，消除三文件不一致 |
| 4 | 测试 | 新增「现场 runner 高于包基线」回归：编译计划断言 handoff 用现场镜像；同版本重装后 runner 版本不变 |

**验收**：`.3` 后端全量 + `.12` 装 v0.3.2 → 同版本重装 → runner 仍 v0.3.2（当前行为会回 v0.3.1）。

**回滚**：还原 4 处改动，无数据迁移、无版本号变化。

## 2. US-27 逃生门只改状态、不收尾

**目标**：`recovery/fail` 让管理员知道"环境半迁移了，要再跑一次升级收尾"。**因放弃人工回滚，本条升级为关键路径**（这是失败后唯一的自愈出路）。

**明确不做**：不自动触发收尾升级（升级必须由人显式发起，不能由失败路径自动再跑一次升级）。

| # | 位置 | 改法 |
| --- | --- | --- |
| 1 | `execution.py::recovery_fail`（stuck_running 分支） | 响应/任务视图加 `cleanup_required: true` + `residual_paths`（探测到的 legacy 路径清单） |
| 2 | 同上 | `error` 文案点明"需再跑一次成功升级，由 post-cleanup 收尾" |
| 3 | 前端升级中心 | 任务失败提示里显示「需收尾」与残留路径（遵循 `docs/frontend-style-guide.md`，不引入新色值） |
| 4 | 测试 | 断言 stuck_running 场景响应含 `cleanup_required` 与残留清单；正常 recovery 场景不含 |

**边界**：不做"标记失败并清理残留"的动作（清理涉及 legacy 删除，风险高于收益，另议）。

**回滚**：还原 4 处，纯提示层。

## 3. US-28 组件升级后写锁窗口致 web-api 裸 500

**目标**：锁窗口内不再 500，返回可读提示 + 自动重试。

| # | 位置 | 改法 |
| --- | --- | --- |
| 1 | `backend/app/v2/database.py` 连接层 | `sqlite3.OperationalError: database is locked/busy` → 指数退避重试（3~5 次，累计 ≤ 数十秒），超时后抛业务异常 |
| 2 | 升级相关 API 错误映射 | 锁超时 → `HTTP 503` + 可读文案「数据库正忙（升级后短暂窗口），请稍后重试」，不再裸 500 |
| 3 | 升级 UI | 503 显示为可重试提示，非"系统错误" |
| 4 | 测试 | 注入锁场景单测（mock 连接超时）断言重试次数与 503 文案 |
| 5 | 演练脚本 | `scripts/verify_full_upgrade_chain.py` 组件步后显式等锁释放（治标，独立于产品改动） |

**明确不做（另记，见 §4）**：runner 侧 `_connect()` 连接泄漏治本、SQLite 改 WAL（涉及数据文件格式变更，风险高于收益）。

**回滚**：还原 4 处。
