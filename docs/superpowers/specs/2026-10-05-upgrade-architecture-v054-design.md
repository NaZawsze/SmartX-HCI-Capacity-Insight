## 2. 目标与非目标

**目标**（本轮验收口径）：
1. runner 执行期**零业务 SQLite 写**（心跳/租约/进度全部走状态文件）——US-28/#82 根治；
2. 平台升级**只重建有差异的服务**，未变更服务容器 ID 不变（含 runner）——US-26 结构性消失，固定回归用例锁死；
3. **回滚三场景可用且实测过**（失败自动回滚 / 成功后手动应用回滚 / 整备回滚）——US-17 关闭，回滚能力成为产品功能而非应急手段；
4. 每次打包自动证明「计划 ⊆ 已发布 runner 能力」；
5. 升级上来的存量站点获得 US-37 守卫（US-39 关闭）。

**非目标**（明确不做，防止范围膨胀）：
- blue/green 双 project 原子切换（磁盘代价大，回滚剧本先行）；
- N-2 兼容计划（兼容债过重）；
- 执行者彻底解耦（options 方案 D，架构级投入，另立项）；
- 4 份 compose 变体合并为 base+overlay（独立立项，本设计只保证"守卫+收敛"使混用无害化）；
- 僵尸任务/残留清理的进一步产品化（已有 US-09 基础，另列）。

## 3. 设计 1：Runner 状态出库（状态文件 + 单写者规则）

### 3.1 状态文件

- 路径：容器内 `/data/upgrade-runner-state.json`（宿主机 `app/upgrade-runner-state.json`）。
  选 app/ 根下**单文件**：runner 与 web-api 共享同一 `/data` 挂载；避开 app/ 下的挂载载体目录（UPG-050 红线只涉及那 5 个子目录，根下放普通文件安全）。
- 内容：

```json
{
  "runner_id": "...", "runner_version": "v0.3.2",
  "started_at": "...", "heartbeat_at": "...",
  "current_task": {
    "task_id": "...", "lease_owner": "...", "lease_expires_at": "...",
    "revision": 42, "checkpoint": { "...": "..." }
  }
}
```

- 写入：临时文件 + `fsync` + `os.replace` 原子替换；每次心跳（5s）与每次步骤推进时全量重写（文件 < 64KB，开销可忽略）。
- 自愈：启动时文件缺失/损坏（JSON 解析失败）→ 视为无状态启动，重建文件；web-api 侧读失败 → 回落现有 docker 检查兜底（`RUNNER_PRESENCE_SOURCES` 已有）。

### 3.2 单写者规则（根除 US-24）

| 对象 | 写者 | 读者 |
| --- | --- | --- |
| `task.json` | **创建时=web-api；执行期=runner 独占** | web-api 只读（投影） |
| `tasks` 表（业务库） | **web-api 独占**（从 task.json 投影状态） | 前端/任务中心 |
| 状态文件 | runner 独占 | web-api 只读 |

- runner 删除 `_project_task` 对 `tasks` 表的写（`main.py`）；web-api 的监督/状态轮询从 task.json 投影到 tasks 表。
- 业务库从此只有 web-api 一个进程写升级相关表。

### 3.3 兼容性（关键，expand–contract）

现场将长期存在「v0.5.3 web-api + v0.3.2 runner」组合（客户先升组件、缓升平台）：

- **v0.3.2 runner 保留 DB 心跳双写，但降级为 best-effort 兼容镜像**：写失败（锁/任何异常）→ 日志 + 跳过，**绝不 crash、绝不重试阻塞**（#82 的兜底语义保留）。状态文件是事实源。
- v0.5.3 web-api 的 presence/precheck 读 DB 心跳 → 兼容镜像保证其工作；v0.5.4 web-api 读**文件优先、DB 兜底**（覆盖 v0.5.4+v0.3.1 组合：v0.3.1 只写 DB）。
- **收缩（contract）**：当 v0.5.3 web-api 退出支持矩阵（约 v0.5.6），v0.3.3 移除 DB 双写。登记为收缩清单，本版不做。

### 3.4 为什么这样分配

- US-28 的实质伤害来自"长事务/连接泄漏 + 全文件锁"，心跳高频小写在修好连接关闭后本已无害，**真正必须出库的是租约与执行状态**（它们决定"谁在执行、恢复点在哪"，被锁死时升级就卡死）；
- 心跳双写保留 v0.5.3 兼容，避免"升了组件、平台预检查却报心跳丢失"的自伤（历史上 US-04/US-26 全是这类组合错配）。

## 4. 设计 2：compose 收敛（diff 驱动，US-26 根治）

`compose.apply` 行为升级（动作类型与参数**不变**，老编译器零感知）：

1. `docker compose -f base -f override config` 得到期望配置，对每个 service 计算规范化哈希；
2. `docker inspect` 该 service 现有容器（config-hash label、image ID）；
3. **只对期望≠实际的服务执行 `up -d --no-deps <svc>`**；一致的服务仅校验 running 并记录"未变更"；
4. **runner 触碰守卫（双保险）**：diff 含 `upgrade-runner` 服务 → 拒绝该服务并记 warning（编译器本就排除 runner，此处防编译器回归）；
5. 差异清单写入任务日志：`将重建: web-api, collector-worker；未变更: frontend, prometheus, upgrade-runner`（可审计、可对账）。

验收判据（固定回归用例）：**平台升级后，未变更服务（prometheus、upgrade-runner）容器 ID 不变**。

## 5. 设计 3：回滚方案（三场景，US-17 关闭）

### 5.0 基础机制（三个场景共用）

- **回滚锚点**：升级任务提交时记录 `{previous_version, previous_image_tags(web-api/collector/frontend), backup 路径+SHA, 升级前已执行迁移快照}`，随任务记录持久化；
- **回滚动作**：`compose.override` 指回旧 tag（旧镜像不删——49-24 回滚保护清单）→ `up` → `health.http`/`health.prometheus` 健康门 → 业务计数 vs 备份 manifest 守卫；
- **旧版可运行前提**：schema 迁移 **expand-only**（只加列/加表；删列/改类型/清理一律延后到 contract 步骤，registry 门禁断言）。
  这是"应用回滚不丢数据"能成立的唯一基础，也是回滚窗口的边界。

### 5.1 场景 A：升级失败自动回滚（升级中，系统自动）

- 计划级语义：`healthcheck` 失败 → 不直接 `failed`，自动进入回滚子计划（5.0 动作）→ 成功 = `rolled_back`（**完整保留失败证据与日志**，US-09 教训：宁留记录）；回滚本身失败 = `rollback_failed` → 进现有 recovery 流程。
- manifest 新增可选字段 `rollback_on_failure`（默认 true）；`schema_version` 不变（老编译器忽略未知字段）。
- **首升局限（如实声明）**：v0.5.3→v0.5.4 的计划由 v0.5.3 老编译器生成，不含自动回滚——该次升级失败大多是"停在旧版"（compose.apply 失败=旧容器还在），危险窗口（新容器起但不健康）靠现有 recovery/手动路径兜；自动回滚从 **v0.5.4 之后的升级**开始全程生效。
- 触发条件严格化：只在 `healthcheck` 及之后步骤失败时回滚；`image.load`/`filesystem` 阶段失败不滚（旧容器根本没动）。

### 5.2 场景 B：升级成功后用户手动回滚——应用回滚（保数据）

- 入口：升级中心「回滚到上一版本」按钮 → 走任务状态机（**单飞守卫适用**）。
- 语义：**只回滚应用、不动数据**——expand 窗口保证旧代码可运行在新 schema 上；回滚后自动补一次采集。
- **可回滚性判定**（产品内明示"可回滚/不可回滚+原因"）：
  1. 旧版本镜像仍在本地（回滚保护清单）；
  2. 自升级以来未执行过任何 contract 迁移；
  3. 当前无进行中升级任务。
- 边界：只支持**回滚到紧邻上一版本**（N-1）；跨两个版本需要跨版本数据兼容，明确不支持。

### 5.3 场景 C：整备回滚（应用+数据回到升级前）

- 语义：恢复升级前备份（SQLite + Prometheus + `.env` 配对），**丢失升级时刻至今的采集数据**——必须显式确认并提示丢失窗口时长。
- 流程产品化 `docs/backup-recovery.md` 恢复五步：停写方 → 恢复备份 → 指回旧 tag → 起服务 → 校验（integrity + 计数）。
- 适用：场景 B 不可用（执行过 contract 迁移）或数据本身被新版本污染时。

### 5.4 共同约束

- 回滚也是升级任务：审计、日志、任务中心投影、US-23 单飞全部适用；
- 回滚锚点/备份的保留期 ≥ 一个回滚窗口（backup_retention 参数联动，#78 已有基础）；
- 每次回滚后在 CHANGELOG/任务记录标注（便于追溯版本漂移）。

**演练矩阵（`.14` 真机）**：镜像加载后失败 / compose up 后不健康 / post-verify 失败（场景 A 的三个失败点）+
场景 B 手动回滚一次 + 场景 C 整备回滚一次 → 判据：旧版本恢复健康、数据符合所选场景的预期（B 保数据/C 回到备份点）。US-17 空白格关闭。

## 6. 设计 4：构建门禁 + 版本偏斜矩阵

- 新增 `scripts/verify_upgrade_plan_runner_compatibility.py`：
  - 输入：候选平台包 + **已发布** runner 组件包（Release 资产，非开发树）；

  - 断言 ⊆ 已发布 runner 包 manifest 的动作集/能力集，缺失即 exit 2；
  - 接入 `ops/package.sh`（身份门禁之后）。从此"新版本能否从老版本升上来"是**构建时机械判定**。
- 偏斜矩阵落 `docs/upgrade-chain.md`：每格 (源版本 × 已发布 runner) 标 ✅实测 / 📋门禁覆盖 / ⛔不支持。
- manifest 纪律：`schema_version` 不经"桥版本"不得变更（老编译器必须能读）。
