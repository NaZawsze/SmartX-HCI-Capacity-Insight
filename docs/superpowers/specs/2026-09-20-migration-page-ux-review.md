# 数据迁移页面梳理与 UI 优化输入

状态：梳理稿（2026-09-20），作为数据迁移页 UI/文案优化的设计输入。**第一批（术语客户化 + 页底使用说明）已实施并验证（2026-09-20，提交 ff7c553，见 progress.md 49-26）**；三区结构重组与健康检查常驻化留待后续批次。
来源：用户反馈「这个界面其实很不明所以……我自己都忘了做什么用的——健康检查是什么，导出配置迁移包是什么，导出迁移包又是什么？补全缺失数据是什么，覆盖导入又是什么？下载恢复密钥，之间的关系是什么」。
准确性说明：本文所有行为描述均逐条核对 `backend/app/v2/migration/service.py` 与 `frontend/src/components/service/MigrationSection.tsx` 现状代码，不是凭印象写的。

---

## 1. 这个页面到底管什么

一句话：**负责"业务数据"的搬出、搬进和落地体检**。它和「平台升级」（换软件版本）无关，和「服务重启」（让导入的数据生效）是配合关系。

"业务数据"在本平台 = 三位一体：

| 组成 | 存在哪 | 丢了会怎样 |
| --- | --- | --- |
| Tower/集群配置（含凭据密文） | SQLite 的 towers/clusters 表 | 不知道该连哪些 Tower，采集停 |
| 历史容量时序 | Prometheus 数据目录（按时间分 block） | 趋势/增长/预测图表全空 |
| 当前状态缓存 | SQLite 的 vm_latest/vm_volumes 等表 | 下次成功采集自动重建，**不丢真数据** |

## 2. 两个核心对象：迁移包和恢复密钥

### 2.1 迁移包（.tar.gz），两种规格

| | 导出迁移包（全量） | 导出配置迁移包 |
| --- | --- | --- |
| Tower/集群配置 | ✅ | ✅ |
| Prometheus 历史时序 | ✅ 全部 block | ❌ |
| 包体积 | 大（随历史增长） | 很小（KB 级） |
| 用途 | 搬家/备份/整机接管 | 新环境快速接入同一组 Tower |
| 任务中心标题 | 导出迁移包 | 导出配置迁移包 |

**包里没有的东西**（核对 tempfile_sqlite_copy：两种包的 SQLite 载荷都只有 towers/clusters 两张表）：平台用户、当前容量表（vm_latest/vm_volumes）、采集运行记录、报表产物。当前容量在导入后由下一次成功采集自动重建；全量包恢复后趋势图表立即可用（直接读 Prometheus 历史）。

### 2.2 恢复密钥（即 project/.env 的快照，UI 不应出现".env"字样）

- Tower 凭据在包里是**密文**，解密钥匙 = 部署时生成的 `.env` 文件。恢复时**包和密钥必须同代配对**。
- 密钥**不打进包**（安全红线：包会流转，密文和钥匙分离，包泄露解不开）。
- 本次 49-25 新增的自动化：**每次导出（全量/配置）自动生成与包同名的密钥快照**，任务中心附「配对 .env（恢复时必须同代使用）」下载链接；页面头部另有「下载当前 .env」随时下载当前生效的密钥。
- 没带密钥的后果与补救：采集解密失败 → 到 Tower 设置页逐个重输密码即恢复（配置、集群、历史数据都在，损失仅"重敲几遍密码"）。平台登录不受影响（登录密码在库内，哈希存储）。

## 3. 界面元素逐一说明（对照现状截图）

### 头部三个按钮

| 元素 | 真实行为 | 什么时候用 | 常见误解 |
| --- | --- | --- | --- |
| **健康检查** | 只读体检：业务库文件在不在、Prometheus 有多少个历史 block、两者齐不齐（complete）。**不改任何数据**，结果在任务中心展示 | 导出前确认源头可导；导入后确认落地完整 | 以为会"修复"什么；以为和 Tower 连接有关（无关） |
| **导出迁移包**（主按钮） | 全量打包：配置+历史 → 浏览器下载 + 服务器 `exports/migrations/` 留档 + 自动生成配对密钥快照；产生任务中心任务 | 换机迁移、定期备份、升级前留档 | 以为含平台用户/报表（不含）；以为 .env 在包里（不在，密钥单独配对） |
| **导出配置迁移包** | 只打包 Tower/集群配置，不含任何历史数据 | 新环境快速接入同一组 Tower；把拓扑配置交给他人 | 和"导出迁移包"什么关系说不清（见 §5 问题 2） |
| **下载当前 .env**（本次新增） | 下载当前生效的密钥文件，需登录 | 补配历史包的密钥；手工留一份钥匙 | 名词看不懂（.env 是黑话） |

### 导入区（选择文件 → 选模式 → 导入）

| 元素 | 真实行为 | 危险等级 |
| --- | --- | --- |
| **选择迁移包** | 上传 .tar.gz/.tgz，包内 manifest 校验格式 | 无 |
| **补全缺失数据**（默认） | 合并模式：只往里加——同名 Tower/集群**不覆盖**（INSERT OR IGNORE），Prometheus 只复制本机缺的 block | 低 |
| **覆盖导入**（需勾选「我确认覆盖当前系统数据」） | 整库替换：smartx.db 直接覆盖 + Prometheus 目录整体替换 | **高（删除性）** |
| 导入前备份（自动，两种模式都有） | 先把当前 smartx.db + Prometheus 打成 `backups/import-before-<时间戳>.tar.gz`，任务中心给路径；失败会阻止导入 | 安全网 |
| 导入后健康检查（自动） | 导入完自动跑一次 §3 健康检查，结果进任务记录 | — |
| **服务重启提示** | 导入只改了磁盘文件；web-api/collector-worker/Prometheus 在内存里的状态不会自动刷新，所以导入后必须在本页执行「服务重启」才完全生效 | 忘了重启 = "导入了怎么没变化"的最常见原因 |

## 5. 现状问题清单（用户困惑点的根因）

1. **动作不带后果**：按钮只有"做什么"，没有"会发生什么"。用户无法从界面推断覆盖导入会删数据、补全不会。
2. **两个导出并列同权重，主次颠倒**：全量是主路径，配置导出是低频辅助，但两按钮并排且配置在前，用户自然要问"配置迁移包是什么、和另一个什么关系"。
3. **"健康检查"无对象说明**：检查什么、结果在哪看、和 Tower 连通性有没有关系（没有）都没交代。
4. **模式命名是"机制"不是"后果"**："补全缺失数据/覆盖导入"描述的是实现方式；用户需要的是"只加不删 / 会替换现有数据"。
5. **".env"黑话**：客户不知道 .env 是什么，本次新增的按钮直接暴露了内部文件名。
6. **页面缺"迁移包里有什么"的总说明**：没有一处告诉用户包含配置+历史、不含用户和报表，用户只能猜。
7. **密钥与包的配对关系不可见**：导出成功后没有"这两份文件要一起保存"的引导，恢复密钥的下载入口藏在头部按钮里。
8. **服务重启提示淹没在页面底部**：这是导入流程的必要收尾步骤，但只是一个蓝色提示条。

## 6. UI 优化方向建议（供立项，未实施）

### 6.1 结构重组：按"导出 / 导入 / 环境状态"三区

- **导出区**：全量导出为主卡（说明"包含 Tower 配置 + 全部历史数据"），完成后弹两步清单：「恢复需要两份文件：① 迁移包 ② 恢复密钥，已自动生成，请一起保存」+ 两个下载按钮。配置导出降级为卡内次要入口（"只要 Tower 配置、不带历史数据 →"）。
- **导入区**：两个模式做成可选卡片而非同名 toggle——「只补缺的（现有数据不动）」/「整库替换（会清空现有数据，需确认）」，危险项红色边框 + 现状警告。导入完成后任务结果里给"下一步：去服务重启"的直达链接。
- **环境状态区**：把健康检查结果变成常驻展示（业务库 ✅ / 历史指标 N 个 block / 完整性），"健康检查"降级为"重新检查"刷新按钮。用户不点也知道环境状态。

### 6.2 术语替换（UI 层，文档/接口层不变）

| 现状 | 建议 |
| --- | --- |
| .env / 下载当前 .env | 恢复密钥 / 下载恢复密钥 |
| 配对 .env（恢复时必须同代使用） | 恢复密钥（与迁移包成对使用） |
| 健康检查 | 环境体检（或保留，但加结果常驻区） |
| 补全缺失数据 | 只补缺的（现有数据不动） |
| 覆盖导入 | 整库替换（清空现有数据） |
| 迁移包 | 保留，但首次出现加副标题「含 Tower 配置与历史数据的备份文件」 |

文件名保持机器可读（`*.tar.gz` + 同名 `.env` 快照），只在**展示层**翻译成客户语言。

### 6.3 不变的边界

- .env 不进迁移包（密文/钥匙分离）；0600；下载需登录。
- 覆盖导入前强制自动备份；缺确认勾选直接 400。
- 导入不自动重启服务（重启是独立显式动作，在服务重启页）。

## 7. 典型场景剧本（写文案时的"用户故事"基准）

1. **换机迁移**：旧机导出全量包+密钥 → 新机装同版本平台 → 导入（覆盖或合并）→ 服务重启 → 体检完整 → Tower 重连验证。
2. **定期备份**：导出全量包 + 密钥，两份一起转存异地；恢复时成对使用。
3. **新环境接入既有 Tower**：导配置迁移包 → 新机合并导入 → 重输/自动解密凭据（带密钥则自动）→ 开始采集，无历史负担。
4. **误操作回滚**：导入出问题 → 任务中心的「导入前备份」路径 → 用该备份恢复。
5. **数据并档**：把另一套环境的全量包在本机用"补全缺失数据"导入，同名不冲突，历史 block 拼接。

## 8. 验收基准（未来改版时用）

- 不看文档的新用户能从界面直接回答：导出会得到什么、两种导出差别、两种导入差别、导入后还要做什么。
- 覆盖导入在未勾选确认前不可触发；危险后果在触发前至少出现一次红色警示。
- 全部导出路径完成后均有"包+密钥成对保存"引导。
- 前端样式遵循 docs/frontend-style-guide.md（:root 变量、6/8px 圆角、分区式表单）。
- 既有测试同步更新后全量回归通过；verify_api_docs 不受影响（无路由变更）。
