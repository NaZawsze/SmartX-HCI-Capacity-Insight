## 2. 目标架构：业界三层映射到本产品

### 2.1 平台升级 =「换镜像 + 健康门 + 留旧回退」（第一层，Harbor/Portainer 模式）

升级固定为**七步常量流程**，全部用 v0.3.1 就有的动作表达：

```text
1. backup.create          # 升级前备份（已有）
2. image.load             # 加载平台三件套新镜像（旧镜像保留）
3. files.sync             # project 文件同步（compose/脚本，含 US-39 守卫脚本投递）
4. compose.override + compose.apply   # 三件套换 tag 重建（diff 收敛，runner 不在范围）
5. health.http/prometheus # 健康门（schema 迁移由新 web-api 启动时自跑，expand-only）
6. post_upgrade.schedule_collection   # 采集冒烟
7. checkpoint/终态        # 证据留档
```

- **26 个动作退役为 8 个通用动作**；`project_migrate`/`runner_handoff`/`stop_legacy`/`task_state` 迁移等
  一次性迁移动作（v0.5.1u2→v0.5.2 桥的历史）对目标布局机器全部不再出现——manifest 不声明
  `environment_transitions/legacy_cleanup`，编译器自然不生成。
- **编译器退役为"常量模板"**：计划 = f(manifest 数据)，无逐版本逻辑——v1 的"计划随包/编译器纯函数化"
  整个议题消失（连计划都基本不存在了）。
- 迁移纪律不变：**expand-only**（只加列/加表），回滚与旧代码兼容的地基。

### 2.2 runner 组件升级 =「kubeadm/Omaha 自换」（第三层）

- 组件包 = runner 镜像 tar + 版本声明，别无他物；
- 流程：web-api 收包验 SHA → 触发 runner → **runner 自己** `image.load` 新镜像 → 写自身 compose 配置 →
  `runner.schedule_target_runtime_handoff`（该动作 v0.3.1 已存在）→ 旧容器被替换、新 runner 起来、回报 presence。
- **web-api 退出组件升级的编排**（stop/交接/守卫整套退役）——US-04 类事故的根源（源端编排杀新 runner）
  结构性消失；组件升级从"一次升级任务"变为"一次 15 秒级的自换"。
- 任务中心仍留痕（谁在何时换到哪个版本），但不再是一个 11 动作的升级任务。
- **后续版本（v0.3.3+）升级 = 同一流程**：自换能力随 v0.3.2 常驻，换刀机制与刀的业务代码正交——
  新镜像带什么新代码都不影响自换动作本身。
- **三条边界纪律**：①组件回滚——自换前旧镜像保留、记回滚锚点，出问题反向自换回旧 tag（同样秒级）；
  ②runner 进程死亡（非升级导致）时退回 web-api 侧兜底重建（现有能力），这是唯一保留 web-api 参与的路径；
  ③**自换协议冻结**——`schedule_handoff` + compose writeback 机制自 v0.3.2 起视为稳定协议，
  后续版本修改其语义必须走"旧路径安装带新机制的新 runner"的桥（与动作词汇冻结同等级的纪律）。

### 2.3 回滚 =「留旧回退」三场景（继承 v1 设计 3，不变）

场景 A 失败自动回滚 / 场景 B 手动应用回滚（保数据，expand-only 前提）/ 场景 C 整备回滚（恢复备份）。
机制层：旧镜像保留 + 指回旧 tag + 健康门 + 计数守卫。细节见 v1 设计 §5（全部有效）。

### 2.4 状态出库 + 单写者（继承 v1 设计 1，不变且更自然）

runner 心跳/租约/进度走状态文件（`/data/upgrade-runner-state.json`，原子写+自愈）；
`task.json` 执行期 runner 独占、`tasks` 表 web-api 独占投影；DB 心跳双写仅作 v0.5.3 兼容镜像（best-effort）。
固定流程让"执行期状态"更薄，状态文件方案更简单。

### 2.5 第二层（appliance A/B）维持非目标

OVA 整机镜像形态是终态方向，等回滚剧本运行一段时间后按客户需求评估，本版不做。

## 3. 退役清单（这次重构删掉什么）

| 退役项 | 替代 |
| --- | --- |
| 计划编译器的逐版本逻辑 | 常量七步模板（manifest 只供数据） |
| `runner_handoff`/`runner.stop_legacy_runtime` 的 web-api 编排 | runner 自换（2.2） |
| `compose.project_migrate`/`legacy.*`（对目标布局机器） | 桥版本已完成使命；动作保留在词汇表仅供旧源兼容 |
| 组件升级的 11 动作任务形态 | 自换 + presence 回报 |
| 两步引导（runner 能力不足时的产品引导） | 仅保留给 v0.3.1→v0.3.2 的一次性旧路径；自换时代无此问题 |

保留：单飞守卫、备份、健康门、presence、US-22 跨重启恢复、任务中心、8 个通用动作、状态出库。

## 4. 兼容矩阵与一次性遗留路径

| 组合 | 说明 |

## 5. 交付批次（重排）

- **批次 A（runner v0.3.2）**：状态文件+单写者 → **自换组件升级** → 回滚机制固化 → US-39 投递 → diff 收敛（保留，作安全垫）。
- **批次 B（平台 v0.5.4）**：presence 文件优先 → 七步常量模板 + 编译器瘦身 → 回滚三场景产品化 → 门禁（动作词汇冻结检查）→ 前端任务中心适配自换形态。
- **批次 C（验收）**：`.14` 全新安装 + 直升（runner 容器 ID 不变）→ v0.3.1→v0.3.2 组件升级（旧路径最后一次）→ **自换组件升级实测（停机时长 ≤ 30s、restarts=0）** → 回滚五项演练 → `.12` 老链路回归 → r18 打包全门禁。

## 6. 测试计划

在 v1 T1–T10 基础上修改：
- T3 保留（diff 收敛回归判据：未变更服务容器 ID 不变）；
- **T11（新）组件自换**：`v0.3.2→v0.3.3-rc` 自换实测——停机 ≤30s、presence 回报 ≤60s、零 web-api 参与；
- **T12（新）七步固定流程**：v0.5.3→v0.5.4 实测计划只含七步、无迁移/handoff 动作；
- 其余（回滚五项、兼容矩阵、全量门禁）不变。

## 7. 风险与回滚

- **最大风险：runner/升级路径同轮大改**。缓解：①七步流程全部使用历经六轮链路演练的既有动作，新代码只是"编排瘦身"；
  ②旧编译器/旧组件路径**保留为兜底**（manifest 缺字段时回落），不删旧路先修新路；
  ③自换机制基于已存在的 `schedule_target_runtime_handoff`（已实测），非新发明；
- 状态文件损坏自愈；DB 兜底继承 v1；
- 设计回滚：`git revert` + 重打包；现场回滚走三场景。

## 8. 决策点（需用户确认）

1. runner 版本沿用 **v0.3.2**（从未交付，governance 允许并入；测试机旧构建由本次验收替换）——用户已口头指定，本设计按此执行；
2. 组件升级形态改为自换后，**组件包瘦身为仅镜像+版本声明**——若未来 runner 需要"迁移自身状态"（本次不需要），再加；
3. appliance A/B（第二层）维持非目标，何时评估由用户定。
