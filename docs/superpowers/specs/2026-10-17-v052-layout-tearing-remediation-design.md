# 设计：v0.5.2 老布局升级后「撕裂态」处置（pending #99）

> 来源：P3 定稿轮 L3-c 实测（`.14`，v0.5.1u2 老布局基线 → v0.5.2）。
> 证据见 `findings.md` 2026-10-17（P3 实测三）、`progress.md` 2026-10-18 节。

## 1. 现象与影响

老布局现场（`/data/smartx-capacity-insight-data/*`，镜像 `v0.5.1u2`）升级到 v0.5.2 后：

| 维度 | 状态 |
| --- | --- |
| 升级结果 | `succeeded`，`.env` 缺陷被 r41 自愈 ✅ |
| 容器挂载 | 变成 `/data/smartx-storage-forecast/*`（**v0.5.2 compose 里的新布局路径**） |
| 实际数据 | 仍在旧布局宿主目录 `/data/smartx-capacity-insight-data/app/smartx.db` |
| 平台读到的库 | 容器 `/data/smartx.db` = 宿主**新布局空库** |
| v0.5.2 镜像的健康检查 | 仍按旧布局子路径 `/data/smartx-capacity-insight-data/app` 判定 → `directories=false / prometheus=false` |
| 后续链路 | CLI 预检健康不过 → **无法继续升到 v0.5.3**；runner 可能还在往旧库写心跳 → 双库 split-brain |

**危害分级**：#93 只是"升级被拒"（失败安全）；本问题是"**升级成功但服务随后读到空库**"——
若现场在 v0.5.2 停留并继续使用，页面数据会归零。**严重度高于 #93**。

## 2. 根因（源码级）

`v0.5.2` 的交付 compose 已把服务挂载写成新布局（为 v0.5.3 目录迁移做准备），
但 `v0.5.2` 镜像内的 `Settings` 仍以 `data_root/smartx-capacity-insight-data/{app,prometheus}`
派生目录，升级动作也没有在 apply compose **之前**把旧布局数据搬到新布局宿主路径。
⇒ 升级本身成功，但"数据位置"与"容器视角"被这一跳撕开。

## 3. 候选方案

| 方案 | 内容 | 能救已发布 v0.5.2 现场？ | 风险 |
| --- | --- | --- | --- |
| **A** | v0.5.4 升级包在检测到撕裂态时，先做目录迁移再 apply compose | ✅（需 v0.5.4 包能被应用到 v0.5.2 → 但预检就过不去，**不可达**） | — |
| **B** | web-api 启动时按实际挂载解析 data_root | ❌ 只能救 v0.5.4+ 的新代码 | 改动面大 |
| **C** | 交付 README 硬约束「v0.5.1u2 → v0.5.2 → v0.5.3 **必须连续执行，禁止在 v0.5.2 停留**」+ 提供救援脚本 | ✅（流程约束） | 依赖人守规矩 |
| **D** | 修改 L3-c 测试基线，用 v0.5.3 起点绕过 | ❌（掩盖问题） | 不可接受 |

**推荐：C（立即）+ B（v0.5.5 收口）**。
- C 立刻可做且直击现场：撕裂态只在新旧布局交替处存在，且 v0.5.3 一跳就会完成目录迁移、
  自动愈合（升级成功后容器按新布局读到的就是刚迁移过来的数据）。
- B 作为结构性收口：让代码不依赖"默认路径"而依赖"实际挂载"，根治"读到空库"这一类错误。

## 4. 验收标准

1. 交付 README（`delivery/README.md` §4 与 `docs/upgrade-chain.md`）写明：老布局现场
   **必须连续升到 v0.5.3**，禁止在 v0.5.2 停留；若已在 v0.5.2 停留，按救援脚本恢复；
2. 救援脚本（`ops/`）：把旧布局数据目录复制到新布局宿主路径（先校验、后复制、保留旧目录），
   重启平台；脚本必须**干跑默认、`--apply` 才执行**；
3. L3-c 链路改为「v0.5.1u2 → v0.5.2 → **紧接着** v0.5.3 → 组件 → r42」，全程不允许中间停留；
   每跳断言：业务表指纹一致 + `.env` 为文件 + 健康检查三项全 true。
