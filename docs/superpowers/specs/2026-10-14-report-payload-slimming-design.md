# 报表接口 payload 瘦身设计（pending #28 第二阶段）

- 日期：2026-10-14
- 来源：pending #28（第一阶段 = 查询去重，2026-09-20 已完成，同进程 A/B 555ms → 288ms）
- 状态：设计（待实施）

## 1. 背景与现状

**现象**（2026-09-20 基线测量，progress 49-26k/m）：报表接口返回体里
**`month_new_vms` 单块约 277KB，占整体 payload 的 63%**——它是「本月新建 VM」的**完整列表**
（全量条目），而页面实际只展示前若干条。

**代码位置**：
- `backend/app/v2/reports/service.py:191-206`：`day_new_vms` / `month_new_vms` 由
  `_new_vm_reports_from_series(...)` 生成后**整体**放进 payload（`"month_new_vms": month_new_vms`）
- 导出侧（`reports/export/word.py` / `excel.py`）**依赖完整列表**（客户报表要全量明细）

**为什么不能直接截断**：同一 payload 被三类消费者共用——① 页面展示（只需前 N 条）
② Word/Excel 导出（要全量）③ API 契约（前端类型）。直接截断会**静默改变导出内容**（不可接受的静默降级）。

## 2. 目标与口径

| 项 | 口径 |
| --- | --- |
| 页面路径瘦身 | 报表接口默认**只返回前 N 条**新建 VM（N 由**服务级契约参数**控制，默认值设计时定，建议 50） |
| 导出路径不受影响 | 导出走**显式全量**参数（如 `?include_full_lists=true`），或在服务层直接调全量函数（不经 HTTP） |
| 显式而非隐式 | 契约参数必须出现在 API 文档与前端类型里；**不允许**"看调用方是谁"的隐式行为 |
| 不改变口径 | 计数类字段（`new_vm_count` 等）**始终是全量口径**——瘦身只裁剪明细列表 |

## 3. 方案（三选一，实施时定）

- **A（推荐）**：接口加查询参数 `new_vm_limit`（默认 50，`0`/`all` 表示全量）。
  页面不传 → 默认瘦身；导出显式传 `all`。契约清晰、可测、可回滚。
- B：拆两个端点（`/reports/summary` 瘦身 + `/reports/full` 全量）——改动面更大，前端要分两路。
- C：仅服务端内部裁剪（页面与导出都走同一函数但传不同 limit）——需保证导出**不经 HTTP**，
  否则仍是隐式行为（不推荐）。

## 4. 边界与不做

- 不改任何统计口径与图表序列（只裁剪明细列表）；
- 不动 `day_new_vms` 的展示逻辑（同为列表，同一参数控制，避免两套规则）；
- 不动 Word/Excel 模板与列结构（Phase 73~78 已定稿）；
- 不做分页 UI（页面本来只显示前几条；需要全量请用导出）。

## 5. 测试计划

| 用例 | 断言 |
| --- | --- |
| 默认瘦身 | 不带参数 → `len(month_new_vms) <= 50`；**计数字段不变** |
| 全量显式 | `new_vm_limit=all` → 列表长度与瘦身前一致（与旧实现逐条对比） |
| 导出不受影响 | Word/Excel 导出的行数与全量口径一致（回归既有导出用例） |
| 契约一致 | `verify_api_docs` 通过（新参数出现在文档）；前端类型同步 |
| 性能 | 同一 `.3` 实例 A/B：payload 体积下降 ≥ 50%（目标：63% 那块基本消失）、响应时间不劣化 |

## 6. 回滚

纯接口参数（默认值即可回退到"全量"语义）→ `git revert` 或把默认值调成 `all` 即恢复原行为。
