# 升级指南

简体中文 | [English](upgrade.md)

版本：`v0.5.4`

本指南覆盖用官方离线交付包升级已有部署。全新部署见[部署指南](deployment.md)。升级中失败的处理见[故障排查](troubleshooting.md)。

## 1. 每次升级都保留什么

升级全程不搬业务数据：

- `app/` 下的 SQLite 业务库。
- `prometheus/` 下的历史时序。
- Tower 配置与凭据（保存在 `app/` + 配对的 `project/.env`）。
- `exports/` 下的报表导出与迁移文件。

平台升级切换前会自动生成当前版本的备份，因此同版本重装或回滚路径始终可用。即便如此，升级前仍建议自己做一次冷备份：`app/smartx.db` 加配对 `.env`——见[备份与恢复](backup-recovery.md)。

## 2. 两步铁律（先 runner 组件，后平台）

当前发布批次（`v0.5.4`）的升级必须**分两步走，顺序不能颠倒**：

1. **第 1 步 — runner 组件升级**（Web 界面先做）
2. **第 2 步 — 平台升级**（CLI，在第 1 步成功之后）

为什么顺序固定、不能颠倒：

- 平台升级计划中的数据库迁移动作由**现场正在运行的 runner** 执行。
- 新的 runner 组件包内置了能执行这些动作的 runner 构建；较早的已发布基线（或任何更早 runner）不能执行，违序会导致迁移步骤失败。
- runner 的更换只发生在**组件升级**里；平台升级本身从不改动、也不重启 runner。

## 3. 选你的路径

| 当前状态 | 要执行的操作 | 说明 |
| --- | --- | --- |
| 用离线交付包装的全新 `v0.5.4`（runner `v0.3.1`） | 执行一次第 1 步（同一包 `upgrade/packages/` 的 runner 组件包）即到位 | 包内安装 compose 固定为已发布基线；组件升级把现场带到批次 runner 版本 |
| 已部署 `v0.5.3`（runner `v0.3.1`），升到 `v0.5.4` | 第 1 步（v0.5.4 批次 runner 组件包）→ 第 2 步（平台包） | 两步都用 `v0.5.4` 离线交付包 |
| 后续新批次 | 只要该批次交付 README 写明附 runner 组件包，就照两步走；未附则只做平台升级 | 批次 README 始终列明该批次交付物与顺序 |
| 目标布局的 `v0.5.2` 现场 | 先走 `v0.5.2 → v0.5.3`（用它自己的交付包），再按上文的 `v0.5.4` 路径 | `v0.5.3` 升级包或之后新包是否支持从老源一步直升，以 `source_compatibility` 与该批次 README 为准 |
| `v0.5.1u2` 或更老布局 | 走历史链路：`v0.5.1u2 → runner bootstrap → v0.5.2 → v0.5.3`（见早期版本说明），之后再按 `v0.5.4` 路径 | 新交付包不再支持老布局直接到达 |

经验法则：**手里的交付包 README 就是该批次的权威操作手册**——它写明本批次交付了哪些包、按什么顺序执行、支持哪些源版本。

## 4. 第 1 步 — runner 组件升级（Web 界面）

1. 把离线交付包解压到现场，找到 `upgrade/packages/` 里的 runner 组件包（README 列了确切文件名与 SHA）。
2. 打开 Web 界面 `http://<服务器IP>:8080`，用管理员登录。
3. 进入「服务管理 → 组件升级」，上传 runner 组件包。
4. 预检查通过后开始升级，等待任务到达 `succeeded`。
5. 在组件升级历史确认已运行新 runner 版本（或查 `GET /api/admin/component-upgrade/version`）。

注意：

- 同一时刻只允许一个升级任务；先确认没有别的升级任务在排队或运行。
- runner 的自换发生在组件升级任务的最后一步；平台升级不碰它。
- 组件升级中途失败时，现场仍在跑的旧 runner 继续工作；处理根因后重新上传组件包即可。

## 5. 第 2 步 — 平台升级（CLI）

组件升级成功之后：

```bash
cd <解包的交付包根目录>
sudo bash upgrade/upgrade.sh --yes
```

`upgrade/packages/` 里有多个平台包时显式指定：

```bash
sudo bash upgrade/upgrade.sh --package upgrade/packages/<平台包文件名>.tar.gz --yes
```

该脚本通过升级中心 API 驱动整个平台升级（不直接加载镜像、不手工重启容器），并实时输出预检查结果。

同样的流程也可以在 Web 界面做（服务管理 → 上传平台包 → 预检查 → 开始 → 等待 `succeeded`）；两者写的是同一任务中心，按团队习惯选一个入口即可。

## 6. 升级完成后

1. 健康检查：

   ```bash
   curl -s http://127.0.0.1:8000/api/system/health | grep -E '"version"|"runner_version"'
   ```

   `"version"` 是你刚装的平台版本；`"runner_version"` 是第 1 步装的 runner 组件包版本。

2. 五个容器全部 `Up`，`upgrade-runner` 为 `(healthy)`。
3. Web 界面 `http://<服务器IP>:8080` 可打开，可登录。
4. 业务数据完好：仪表盘与虚拟机页面与升级前相同的集群容量与虚拟机数据。
5. 触发一次手动采集并确认成功。

## 7. 回滚

按要撤销的范围，有两条回滚路径：

| 场景 | 恢复什么 | 数据影响 |
| --- | --- | --- |
| **回滚到上一版本（应用回滚，保数据）**——Web 界面原样按钮名 | `web-api` / `collector-worker` / `frontend` 容器回到前一版本 | 业务数据原位保留 |
| **整备回滚（数据回到升级前）**——Web 界面原样按钮名；覆盖 SQLite 与 Prometheus | 前版本容器栈 + 升级前完整数据快照 | 恢复到升级前快照；快照之后采集到的数据会丢失 |

服务管理页面里可查看两者的「回滚可用性」并把回滚作为独立任务发起；**整备回滚**执行前界面会弹出数据丢失窗口（升级时刻至今的采集数据）并要求显式确认。

注意：

- 整备回滚会把数据目录重写到快照状态；升级后采集出的、必须保留的数据要先导出。
- 不要用手工 compose 命令重启容器这种「自造回滚」，回滚一律走本文两条回滚任务。

## 8. 规则与已知坑

- **同一时刻只允许一个升级任务**。存在排队/运行中的升级、回滚、恢复任务时，新任务会被拒绝。
- **runner 停止或重启期间不要做平台升级。**
- **不要用平台升级任务去升级 runner。** runner 版本只能走组件升级。
- **不要手工加载镜像或重启容器**当「补救」；容器状态归升级中心管。
- **容器运行期间不要删除/移动** `/data/smartx-storage-forecast` 下的数据目录。
- **迁移/导出与 `.env` 必须成对保存**；不成对的包无法解密 Tower 凭据。
- 平台升级预检查失败时，先读返回的补救提示（每项检查都会写明发现什么）；不要盲目重试。
- 复跑防呆：同版本平台包重复提交默认被拒，目的是防止误触跳过失败步骤；确需重跑时可用显式放行参数。
