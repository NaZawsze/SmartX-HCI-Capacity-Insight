# Deployment Guide

[简体中文](deployment.zh-CN.md) | English

Version: `v0.5.4`

This guide covers a fresh deployment of SmartX HCI Capacity Insight. For upgrading an existing deployment, see the [Upgrade Guide](upgrade.md); the offline delivery bundle also ships its own README with the bundle-specific procedure.

## 1. Requirements

### Server

- Linux server (validated on openEuler, Debian 13, and CentOS/RHEL 8+).
- `root` or `sudo` permission.
- Docker Engine 20.10 or later with the Compose V2 plugin (`docker compose version` must return a version).
- Recommended: 4 CPU cores and 8 GiB RAM.
- Disk: at least three times the delivery bundle size plus 10 GiB free on the filesystem that holds the data root. All runtime data is stored under `/data/smartx-storage-forecast`.

### Network and ports

- Ports `8080` (web UI), `8000` (API), and `9090` (Prometheus) must be free.
- The server must be able to reach CloudTower/Tower.
- Offline deployment does not need internet access: all images are included in the delivery bundle. Online deployment requires access to Docker Hub.

### CloudTower

- Use a read-only CloudTower account or a read-only API token.
- The CloudTower instance must provide these v2 HTTP API endpoints:

```text
/v2/api/login
/v2/api/get-clusters
/v2/api/get-cluster-storage-info
/v2/api/get-vms
/v2/api/get-vm-volumes
```

- No specific CloudTower minor version is required as long as these endpoints are available and return the expected payloads.

## 2. What gets installed

The platform runs five containers in the Docker network `smartx-hci-capacity-insight-net` (`10.249.251.0/24`, created by Compose).

| Container | Image | Responsibility | Ports |
| --- | --- | --- | --- |
| `web-api` | `nazawsze/smartx-hci-capacity-insight-web-api:v0.5.4` | FastAPI backend: authentication, business queries, reports, data migration, and the upgrade entry point. | `8000` |
| `collector-worker` | `nazawsze/smartx-hci-capacity-insight-collector-worker:v0.5.4` | Scheduled and manual collection from Tower. Writes the latest state to SQLite and exposes metrics on `9108` inside the Docker network. | None published |
| `frontend` | `nazawsze/smartx-hci-capacity-insight-frontend:v0.5.4` | React web interface served by Nginx. | `8080` → `80` |
| `prometheus` | `prom/prometheus:v2.55.1` | Stores capacity time series for trends, growth, and forecast reports. Retention is 400 days. | `9090` |
| `upgrade-runner` | `nazawsze/smartx-hci-capacity-insight-upgrade-runner:v0.3.2` | Executes platform upgrades, component upgrades, backups, health checks, and rollback outside `web-api`. | None |

Runner tag note: `v0.3.2` is the repository / online-install tag. In the offline delivery bundle the install compose pins the published runner baseline of that batch (v0.5.4 batch = `v0.3.1`); the bundled component package in `upgrade/packages/` upgrades it afterwards. See the bundle README for details.

### 2.1 Data directories

All persistent data is stored under `/data/smartx-storage-forecast`:

| Directory | Content |
| --- | --- |
| `project/` | Compose files, Prometheus configuration, and `.env`. |
| `app/` | SQLite business database (`smartx.db`). |
| `prometheus/` | Prometheus time-series blocks. |
| `upgrades/` | Uploaded upgrade packages and upgrade task state. |
| `backups/` | Upgrade and import backups. |
| `exports/` | Report exports and data migration files. |
| `compose-runtime/` | Runtime Compose overrides generated by the upgrade center. |

The installer (or `pre_install.sh` for the source-build path) creates these directories and sets the required ownership. Do not delete or move them while the containers are running — the mount carriers live on the directory inodes, and removing them tears down live mounts machine-wide.

## 3. Deployment steps

There is a single install entry point: **`install.sh`**. It auto-detects the source shape and the acquisition mode:

| Shape | Detection | Default mode |
| --- | --- | --- |
| Delivery bundle | `images/` and `project/` exist next to the script | Offline (verify checksums + load bundled images) |
| Repository | `docker-compose.offline.yml` / `docker-compose.online.yml` exist at the script root | Online (`docker pull` the tags declared in compose) |
| External image directory | `--images <tar dir>` | `--mode offline` |

The same script lives in three places:

| Where you get it | Command | Typical user |
| --- | --- | --- |
| Delivery bundle | `install/install.sh` | Customer sites without internet |
| Repository clone (root) | `install.sh` | Servers with Docker Hub access |
| `ops/install.sh` (repo, for developers) | forwards to the root installer | development iterations on a clone |

### 3.1 Install from the offline delivery bundle (recommended for customer sites)

Unpack the bundle and run the installer as root (the bundle arrives as a directory or as a compressed package with that directory inside):

```bash
tar -xzf smartx-capacity-insight-v0.5.4-offline.tar.gz   # skip if you received the extracted directory
cd smartx-capacity-insight-v0.5.4-offline
sudo bash install/install.sh --yes
```

One command does all of it: root/Docker/port/space prechecks, image checksum verification, loading the five images, creating the data directories, writing `.env` with two randomly generated keys, starting the stack, and waiting for the health check.

Rules:

- Do not modify files inside the bundle; the installer verifies their checksums on every run.
- After the install finishes, follow the printed two-step upgrade note whenever you upgrade later (runner component first, then platform). See the [Upgrade Guide](upgrade.md).

To pick the initial administrator account during installation:

```bash
sudo bash install/install.sh \
  --admin-user admin \
  --admin-password '<initial-password>' \
  --yes
```

### 3.2 Online installation (internet-connected server, no bundle needed)

```bash
git clone https://github.com/NaZawsze/SmartX-HCI-Capacity-Insight.git
cd SmartX-HCI-Capacity-Insight
sudo bash install.sh --yes
```

`.env` is generated by the installer (two random keys plus the initial administrator password); do not run `cp .env.example` or `pre_install.sh` manually.

The installer pulls the images declared in compose from Docker Hub, verifies each tag, and starts the stack. The required tags are the platform `v0.5.4` images (`web-api`/`collector-worker`/`frontend`), the runner `v0.3.2` image, and `prom/prometheus:v2.55.1`.

To install on a server **without** Docker Hub access, prepare the tars for **those five tags** on any connected machine:

```bash
for t in web-api:v0.5.4 collector-worker:v0.5.4 frontend:v0.5.4 upgrade-runner:v0.3.2; do
  docker pull "nazawsze/smartx-hci-capacity-insight-$t"
done
docker pull prom/prometheus:v2.55.1
docker save nazawsze/smartx-hci-capacity-insight-web-api:v0.5.4 > web-api.tar
docker save nazawsze/smartx-hci-capacity-insight-collector-worker:v0.5.4 > collector-worker.tar
docker save nazawsze/smartx-hci-capacity-insight-frontend:v0.5.4 > frontend.tar
docker save nazawsze/smartx-hci-capacity-insight-upgrade-runner:v0.3.2 > upgrade-runner.tar
docker save prom/prometheus:v2.55.1 > prometheus.tar
```

Transfer the five tars plus the repository's `install.sh` (or the whole cloned repository) to the target server and run:

```bash
sudo bash install.sh --mode offline --images /path/to/tars --yes
```

### 3.3 Source build (development only)

```bash
cp .env.example .env
# edit the secrets in .env
sudo ./pre_install.sh
docker compose -f docker-compose.dev.yml up -d --build
```

Do not use this mode for production.

### 3.4 Verify the deployment

Check the API health endpoint:

```bash
curl -s http://127.0.0.1:8000/api/system/health
```

The response must contain `"ok": true`, `"version": "v0.5.4"`, and `"runner_version": "v0.3.1"` for a fresh offline-bundle install, and the `checks` fields `directories`, `database`, `prometheus` must all be `true`. A fresh install from the offline delivery bundle runs the published runner baseline (`v0.3.1`); complete one runner component upgrade with the component package bundled in `upgrade/packages/` (web UI: Service Management → Component Upgrade) before any platform upgrade, after which the health response reports `"runner_version": "v0.3.2"`.

Check the containers:

```bash
docker ps --filter name=smartx-hci
```

All five containers must be `Up`, with `upgrade-runner` reporting `(healthy)`.

### 3.5 First-time configuration

1. Open `http://<server-ip>:8080`, log in as `admin` with the initial password, and change the password immediately (the default password is public).
2. Open `Settings` and add a Tower: name, URL, credentials or API token, and TLS verification enabled. Test the connection.
3. Select the clusters to collect and save the configuration.
4. Trigger a manual collection from the dashboard and confirm that it succeeds.
5. Confirm that cluster capacity and VM data appear on the dashboard and VM pages.

Scheduled collection follows each Tower's own interval; the default is 60 minutes.

## 4. Common install failures

| Symptom | Cause | Fix |
| --- | --- | --- |
| `无法识别安装环境` / "cannot recognize the install environment" | The script was copied out of its bundle/repo context | Run the script from `install/` inside the unpacked bundle, or from a repository clone root |
| Image checksum verification failed | Bundle files were modified or truncated in transfer | Re-transfer the bundle; compare SHA256SUMS |
| Disk space insufficient | The filesystem holding `--install-root` (default `/`) is too small | Free space or pass `--install-root` to a larger filesystem |
| Port already occupied | `8080`/`8000`/`9090` taken by another service | Free the ports or stop the conflicting service |
| `docker` daemon not running | Docker stopped or no permission | Start Docker / run as root |
| Re-run prints or exits without changes | Idempotent guard: a live install already exists | Normal behavior; the existing `.env` and stack are kept |

## 5. Upgrades

Platform batches are installed with the same offline bundle philosophy: a runner component upgrade (when the batch ships one) followed by the platform upgrade, in that order. The [Upgrade Guide](upgrade.md) covers the procedure, supported source versions, post-upgrade checks, and rollback.

The offline bundle's README also carries the bundle-specific upgrade procedure and the packages it ships in `upgrade/packages/`.

## 6. Backup before risky operations

Before upgrades, or any large layout change, take a verifiable backup or at minimum a cold copy of `/data/smartx-storage-forecast/app/smartx.db` plus the paired `.env`. The pairing rule matters most: a migration or export package without its `.env` cannot restore encrypted Tower credentials. See [backup-recovery](backup-recovery.md).

## 7. OVA deployment

> The OVA is not released yet. The procedure below applies once the OVA is published.

The OVA is a ready-to-run virtual machine template for fresh deployments and demo environments. It is not an upgrade package and must not be uploaded to the service management upgrade page.

1. Import the OVA into Tower and power it on.
2. The image has SmartXTools preinstalled. After the VM starts, set its IP address and OS account password directly from Tower; no console login is required.
3. Open `http://<vm-ip>:8080`, log in with the initial administrator account (`admin` / `password`), and change the platform password immediately.
4. Open `Settings`, add the Tower/CloudTower connection, and trigger a manual collection to verify that data is collected.

## 8. Uninstall

Uninstalling deletes all business data and history. Back up first if anything matters.

```bash
cd /data/smartx-storage-forecast/project
docker compose -f docker-compose.offline.yml --env-file .env down   # NOT down -v
rm -rf /data/smartx-storage-forecast        # only after the stack is down
```

Never run `docker compose down -v`.
